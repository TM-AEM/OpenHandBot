# Mini App (OHB2-05/06) — خلفية ASGI + مصادقة initData + ميزات البوت + تحصين أمني

> **النطاق:** الـ Mini App دلوقتي **واجهة عملية** لقدرات البوت (الشاتات، البرومتات،
> الشات الجديد، المتابعات، الإشعارات) — مش تطبيق منفصل. كل الطلبات بتنادي **نفس**
> طبقة الخدمات وقاعدة البيانات بتاعة البوت (مفيش منطق أعمال مكرّر).
> OHB2-06 ضاف كمان: تحصين توقيع initData، تحديد معدّل، حماية Origin، وتحديد IP العميل.

## 1. نظرة عامة

الـ Mini App بيتقدّم من **نفس عملية البوت الواحدة** (OHB2-04 اختار Option A):

```
Telegram WebView ──HTTPS──▶ ingress (TLS) ──HTTP──▶ الحاوية:MINI_APP_PORT
                                                          │
                                        عملية asyncio واحدة:
                                        • long polling بتاع البوت (زي ما هو)
                                        • سيرفر Uvicorn/Starlette (task جنب البوت)
                                        • نفس كائن Database الواحد
                                        • نفس كائن OpenHandsClient
```

- مفيش عملية تانية، مفيش worker تاني، مفيش اتصال SQLite تاني.
- الواجهة والـ API على **نفس الأصل** (same-origin) ⇒ كوكي جلسة `SameSite=Strict` بدون تعقيدات CORS.
- كل الردود JSON، والأخطاء بشكل موحّد `{"error": code, "message": ...}`.

## 2. التبعيات

| الحزمة | الإصدار | ليه |
| --- | --- | --- |
| `starlette` | `0.41.3` | إطار ASGI صغير (راوتنج + responses) بدون أي إطار ثقيل |
| `uvicorn` | `0.34.0` | سيرفر ASGI قياسي، بيشتغل كـ task جوه event loop الموجود |

مقصور إننا **ما ضفناش FastAPI** ولا مكتبة rate-limiting خارجية — كل حاجة صغيرة وبدون تبعيات.

## 3. دمج السيرفر مع عملية البوت

- `bot/app.py::_wire_mini_app` بيربط خلفية الـ Mini App بدورة حياة البوت، **بس لما `MINI_APP_ENABLED=1`**،
  وبيمرّر `client` (OpenHandsClient) و`application` للخدمة (عشان تنبّه الـ workers المالكين الموجودين).
- `bot/web/runner.py::web_server_lifespan`:
  - بيربط الـ socket بنفسه (`_bind_socket`) ويمرّره لـ Uvicorn. كده فشل الربط (منفذ مستخدم)
    يطلع `OSError` عادي ⇒ **التشغيل كله يفشل بوضوح** (fail-fast).
  - بيعطّل `uvicorn.Server.capture_signals` وقت التشغيل المشترك، عشان **البوت** هو اللي
    يمسك SIGINT/SIGTERM ويعمل إغلاق نظيف.
  - `proxy_headers=False` (شوف القسم 9 — قرار أمني مقصود).
- الترتيب في `post_init`: البوت بيعمل تعافيه ويشغّل الـ workers/المراقب **قبل** ما سيرفر الويب
  يبدأ. في `post_shutdown`: السيرفر يقف **قبل** ما البوت يقفل الموارد (`client`, `db`).
- حرس تكرار: إعادة تهيئة مكرّرة (`post_init` اتنادت مرتين) **ما بتبدأش سيرفر تاني**.

## 5. تدفّقات البرومت/الشات الجديد (OHB2-07): idempotency + حالات العملية

المشكلة: إعادة المحاولة من الواجهة (double-tap، أو انقطاع الاتصال بعد ما السيرفر
استلم الطلب) كان ممكن تعمل **برومت مكرّر** أو **شات جديد مكرّر**. الحل بيبني على
الصندوق المتين الموجود (مفيش مسار إرسال جديد):

- **معرّف عملية من العميل (`client_ref`)**: الواجهة بتولّد معرّف فريد لكل عملية
  (نفس المعرّف بيتعاد في كل إعادة محاولة لنفس النص). الـ API بيقبله في
  `POST /conversations/{id}/prompt` و`POST /chats`.
- **idempotency على مستوى القاعدة**: `add_or_group_outbox` و`add_creation_job`
  بيرجّعوا نفس السجل لو نفس `(conversation_id/chat_id, client_ref)` موجود —
  فإعادة الإرسال بنفس المعرّف ما بتعملش سجل تاني (عمود `client_ref` جديد، غير مدمّر).
- **حالات العملية**: `GET /operations/outbox` و`GET /operations/creation` بيرجّعوا
  DTO آمن (مفيش نص البرومت ولا تفاصيل داخلية): `pending` / `accepted` / `failed` /
  `ambiguous` / `unknown`. الاستعلام ممكن بـ `id=` أو بـ `client_ref=` (بعد نتيجة غامضة
  من غير ما نعرف الـ id).
- **النتيجة الغامضة**: لو الاتصال اتقطع، الواجهة **ما بتعيدش الإرسال تلقائياً** —
  بتستعلم عن الحالة الأول (GET آمن)، وإعادة الإرسال يدوية صريحة بنفس المعرّف
  (idempotent، مفيش تكرار). عند القبول، إنشاء الشات بينقّل لصفحة التفاصيل.
- **دورة حياة المعرّف (OHB2-07-FIX)**: منطق توليد المعرّف معزول في وحدة مستقلة عن
  الـ DOM (`bot/web/static/ops.js`) ومُختبرة بـ Node. القاعدة: عملية **نشطة**
  (`pending`/`ambiguous`) بنفس المفتاح ⇒ نفس المعرّف؛ عملية **نهائية**
  (`accepted`/`failed`) ⇒ أول إرسال جديد بنفس المفتاح ياخد **معرّف جديد**. مفتاح
  البرومت = `(conversation_id, text)`، ومفتاح إنشاء الشات = `(repository, text)` —
  فالفشل أو النجاح السابق **مايلغيش** عملية جديدة، وطلب نفس النص في **مستودع مختلف**
  عملية جديدة. الاختبارات: `tests/frontend/ops.test.js` (شوف §12).

## 6. إعادة استخدام منطق البوت (مفيش تكرار)

`bot/web/services.py::MiniAppService` هي الطبقة الرقيقة الوحيدة فوق المكوّنات الموجودة:

| عملية الـ Mini App | المنطق المُعاد استخدامه |
| --- | --- |
| قائمة الشاتات | `OpenHandsClient.search_conversations` + نفس كاش البوت القصير (`list_cache`) |
| تفاصيل شات | `get_conversations` + `get_last_exchange` + `messages.get_status/state_label/truncate` |
| إرسال برومت | **`db.add_or_group_outbox`** (نفس الصندوق المتين + التجميع) ثم `worker.wake()` |
| شات جديد | **`db.add_creation_job`** ثم `worker.wake()` |
| متابعة/إلغاء | `db.add_watched` / `db.remove_watched` (أو `watcher.unwatch` لو موجود) |
| الإشعارات | `db.get/set_notifications_enabled` |
| الحالة | `messages.get_status` (نفس مصدر الحقيقة) |

- **مفيش إرسال مباشر من الـ API**: البرومتات والشاتات الجديدة بتمر بنفس الـ workers المالكين
  (at-most-once، تعافي عند إعادة التشغيل، تجميع) — مفيش ازدواج ولا سلوكين مختلفين.
- الخدمة **ما بتبدأش أي worker**؛ بس بتنبّه الموجود عبر `application.bot_data`.

## 7. تدفّق المصادقة (initData) + التحصين (S1)

بيتّبع [إجراء تيليجرام الرسمي](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app):

1. الواجهة تاخد `Telegram.WebApp.initData` الخام (**مش** `initDataUnsafe`) وتبعتها في `POST /api/v1/auth`.
2. السيرفر (`bot/web/initdata.py`):
   - يشتق المفتاح السري: `secret = HMAC_SHA256("WebAppData", bot_token)`.
   - يبني `data_check_string` (كل الحقول ما عدا `hash`/`signature`، مرتبة أبجديًا، مفصولة بـ `\n`).
   - **S1 (OHB2-06):** يتحقق إن `hash` **64 حرف hex بالظبط** (`^[0-9a-fA-F]{64}$`) **قبل** أي مقارنة.
     أي قيمة فاضية/قصيرة/طويلة/غير hex/بأحرف غير ASCII ⇒ `InitDataError` منظّم (401)، وما توصلش
     لـ `hmac.compare_digest` (اللي كان بيرمي `TypeError` ⇒ 500).
   - يقارن بمقارنة **ثابتة الزمن** (`hmac.compare_digest`)، وملفوفة في `try` كأمان إضافي.
   - يتحقق من `auth_date`: يرفض المستقبلي (بهامش 30 ثانية) ويرفض الأقدم من `MINI_APP_INITDATA_MAX_AGE`.
   - **بعد** نجاح التوقيع بس بيقرأ `id` المستخدم من حقل `user`.
3. لو التحقق نجح **و** الـ id ∈ `ALLOWED_TELEGRAM_ID` ⇒ توكن جلسة عشوائي (opaque)
   في كوكي `ohb_session` (`HttpOnly; Secure; SameSite=Strict; Path=/`).
4. الطلبات اللاحقة بتيجي بالكوكي؛ السيرفر يدوّر على الجلسة في **مخزن في الذاكرة** (TTL).
5. `logout` بيلغي الجلسة ويمسح الكوكي.

### ضمانات أمنية

- مفيش ثقة في أي `id` جاي من الجافاسكريبت — بيُقرأ بعد التوقيع، وبيتحقق من `ALLOWED_TELEGRAM_ID`.
- مفيش بيانات مصادقة في `localStorage`؛ الجلسة كوكي HTTP-only فقط.
- مفيش أسرار أو توقيعات في الكوكي نفسه (توكن عشوائي، والسيرفر هو اللي يعرف معناه).
- مستخدم غير مسموح ⇒ `403` (ومفيش أي تفاصيل حساسة في الرسالة). أي جلسة لمستخدم اتشال من
  القايمة بتتبطّل وتترفض.

## 8. تحديد المعدّل (S2)

`bot/web/ratelimit.py::SlidingWindowLimiter` — نافذة منزلقة في الذاكرة، بدون تبعيات، بساعة قابلة للحقن.

- **`/auth`:** لكل **IP** — افتراضيًا **10/دقيقة** و**30/ساعة** (`MINI_APP_AUTH_RATE_PER_MINUTE`,
  `MINI_APP_AUTH_RATE_PER_HOUR`).
- **باقي الـ API المصادَقة:** لكل **جلسة** — افتراضيًا **60/دقيقة** (`MINI_APP_API_RATE_PER_MINUTE`).
- التجاوز ⇒ **`429`** مع هيدر **`Retry-After`** صحيح (بالثواني).
- **الانفجارات مسموحة**: الحدود متسامحة مع دفعات صغيرة، والواجهة بتعمل retry واحد بسيط (700ms)،
  فالاتصال الضعيف ما بيتعاقبش.
- **تنضيف المدخلات المنتهية**: كل فحص بيشيل الطوابع الأقدم من أوسع نافذة.
- **حد للذاكرة**: `MINI_APP_RATE_MAX_KEYS` (افتراضي 4096) مع طرد الأقدم (LRU) ⇒ مفيش نمو بلا حد.
- **`/health` والأصول الثابتة مش متحدّدين** عشان فحص الصحة وتحميل الواجهة يفضلوا شغالين.
- **مفيش تسجيل بيانات حساسة**: المفاتيح معرّفات مستعارة (توكن الجلسة أو `ip:...`)، مش توكنات.
- الطلب المرفوض **ما بيتسجّلش** (عشان ما يمدّدش الحظر).

## 9. تحديد IP العميل + الـ proxy (S3)

**اكتشاف فعلي (probe على الـ runtime):** الـ ingress (Traefik) **ما بينضّفش** أي `X-Forwarded-For`
جاي من العميل — بيعمل **إلحاق** للند الحقيقي على اليمين:

```
عميل مزوّر:  X-Forwarded-For: 203.0.113.7            (من العميل)
اللي وصل:    X-Forwarded-For: 203.0.113.7, 10.1.1.62 (Traefik لحق 10.1.1.62)
وكمان:       X-Real-Ip: 10.1.1.62 ، TCP client = 10.2.97.6 (hop داخلي تاني)
```

النتيجة: `X-Forwarded-For` كله **غير موثوق** هنا. لو منحنا Uvicorn ثقة (`proxy_headers=True`)،
كان هياخد أول قيمة غير موثوقة من اليمين = **القيمة المزوّرة من العميل** ⇒ انتحال IP.
لذلك:

- **`proxy_headers=False`** في `bot/web/runner.py` — بنستخدم `request.client.host` (الند الحقيقي).
- `bot/web/clientip.py::resolve_client_ip` بيسقط أي IP محلي/غير صالح تحت مفتاح واحد `"unknown"`.
- **القيد الموثّق:** في الـ topology دي، كل العملاء المباشرين بيمرّوا عبر نفس الـ hop الداخلي،
  فـ IP المستخدم النهائي **مش ممكن نستخرجه بثقة**. يعني تحديد المعدّل «لكل IP» بيقرب من «عام».
  ده **الخيار المتحفّظ الآمن (fail closed)**: ما بنصدّقش أي هيدر يزوّره العميل، وما بنفترضش إن IP
  شفناه هو المستخدم النهائي. لو النشر بقى خلف proxy موثوق إحنا نتحكّم فيه، بيتضاف نطاقه هنا
  ونستخدم XFF بأمان.
- **افتراض النشر:** الـ Mini App خلف ingress واحد بيتحكم فيه المشغّل، والوصول مقصور على المالك
  المسموح بعد مصادقة initData. تحديد المعدّل دفاع إضافي (طبقة داخل العملية)، مش خط الدفاع الوحيد.

## 10. حماية Origin (S4)

طلبات **تغيّر الحالة** لازم تكون من أصل مسموح (`bot/web/app.py::_origin_ok`):

- `Origin` لازم يطابق `mini_app_allowed_origins` (بتتشتق من `MINI_APP_URL`، أو صريحة في
  `MINI_APP_ALLOWED_ORIGINS`). شبكة أمان للتطوير: نفس الـ host المطلق.
- `Sec-Fetch-Site: cross-site` ⇒ رفض فوري (إشارة إضافية، مش بديل عن فحص الـ Origin).
- الطلبات **قراءة** (GET) ما بتتطلبش Origin.
- `SameSite=Strict` **ما اتضعّفش** — ده خط دفاع أول، وفحص الـ Origin خط تاني.
- الرد الرفض: `403 {"error": "bad_origin"}`.

### تفويض ملكية الشات (OHB2-09-A2-02)

كل مسار بيوصل لبيانات شات **محدّد** في الـ Mini App بيمر من تفويض ملكية واحد
(`bot/files.py::authorize_conversation` عبر `MiniAppService._authorize_conversation`)
**قبل** أي قراءة أو أثر جانبي: `/conversations/{id}`، `/status`، `/cost`، `/files`،
`/file`، `/prompt` (POST)، و`/watch` (POST). القرار:

- الشات لازم يكون موجود ومملوك لهوية المالك الحالية (`/users/me`)؛ غياب المالك أو
  اختلافه ⇒ `403 unauthorized` (فشل مغلق). معرّف غير صالح ⇒ `400`. شات مش موجود ⇒ `404`.
- `POST /conversations/{id}/prompt` بيفوّض **قبل** تسجيل أي برومت في الصندوق، فمستخدم
  مصادَق (مش المالك) مايقدرش يوجّه برومت لشات مش بتاعه ولا يترك سجل صندوق.
- **استثناء مقصود:** `DELETE /conversations/{id}/watch` (unwatch) **مش** مربوط بملكية
  الشات — عملية على قايمة متابعات المالك نفسه (حالة مالك واحد)، وبتفضل شغّالة حتى لو
  الشات مش موجود/مملوك دلوقتي (تمنع حالة عالقة، وتكافؤ مع أمر البوت). حمايتها: جلسة
  المالك + Origin + معرّف صالح.
- عند فشل التفويض **ما بيتجابش** أي بيانات محمية (آخر تبادل/ملفات/مقاييس) — مُثبت
  بعدّادات النداءات في `tests/test_a2_conversation_authz.py`.

### حذف الشات (OHB2-MINIAPP) — حذف **بعيد** فعلي، نفس دورة الحياة في البوت والـ Mini App

- **المسار:** `DELETE /api/v1/conversations/{id}` (كوكي + Origin، تغيير حالة) ⇒
  `MiniAppService.delete_conversation` ⇒ التنسيق المشترك `bot/deletion.py`، وهو نفسه اللي
  البوت بيستدعيه (زر «🗑 حذف الشات» ⇒ `deleteok:{id}`). **دورة حياة واحدة مشتركة** للواجهتين.
- **التفويض server-side:** تفويض ملكية الشات (`_authorize_conversation`) **قبل** أي حذف —
  مش اعتماد على فحص في العميل. مالك تاني ⇒ `403 unauthorized`؛ غير مصادَق ⇒ `401`؛
  معرّف غير صالح ⇒ `400`؛ غياب Origin ⇒ `403 bad_origin`.
- **الحذف البعيد (المطلوب الأساسي):** النداء `DELETE /app-conversations/{id}` على OpenHands
  نفسه (Bearer)، والنجاح مربوط بتأكيد OpenHands:
  - `200 {"success": true}` ⇒ نثبّت الحذف المحلي + حالة `confirmed` (نفس المعاملة الذرّية).
  - `404` ⇒ **مبهم** (الشات مش موجود فعلًا، أو الخدمة فشلت داخليًا) ⇒ مش نجاح تلقائي؛ بيمر
    بتسوية التحقق من الوجود: غايب (قراءات متتالية) ⇒ نجاح، موجود ⇒ فشل، تعذّر ⇒ معلّق.
  - `400/401/403` ⇒ **فشل مؤكّد** (الشات لسه موجود) ⇒ خطأ منظّم للواجهة (`remote_delete_failed`)،
    **مفيش** حذف محلي ومفيش نجاح كاذب.
  - `429`/`5xx`/انقطاع/رد مشوّه ⇒ نتيجة **مجهولة** ⇒ نسوّي بالتحقق من الوجود (`GET`):
    غايب ⇒ نجاح، موجود ⇒ فشل، تعذّر التحقق ⇒ `503 remote_delete_pending` (الشات متشاهد
    محليًا بس الحذف البعيد لسه مش متأكد).
- **الواجهة:** زر حذف ظاهر ⇒ تأكيد صريح يوضّح إن الحذف **من OpenHands** + زر إلغاء ⇒ بعد
  النجاح نرجع لقايمة الشاتات ونحدّثها. فشل/نتيجة غامضة ⇒ رسالة عربية واضحة + إعادة محاولة
  (idempotent، ومفيش حذف مزدوج). RTL كامل (`dir="rtl"`).
- **منع الإحياء + حالة الحذف الدائمة:** الحذف بيتكتب في **معاملة ذرّية واحدة** بتشيل الأثر
  المحلي (متابعة/صندوق معلّق/إكمال/لقطة إشعار/توجيه) وتكتب **شاهد حذف دائم (tombstone)** في
  `deleted_conversations` مع عمودي `remote_state`/`remote_updated_at` (الوسم `deleting` قبل
  النداء البعيد، وبعدين `confirmed` أو `uncertain`). الشاهد والحالة بيفضلوا بعد إعادة التشغيل.
- **هُوية الشاهد المتينة (OHB2-PR6 — إصلاح TS-1):** تمييز «شاهد قديم» (حذف محلي سابق) عن
  «شاهد محاولة جديدة» **ما بيعتمدش على مقارنة الطوابع الزمنية** (كان عرضة لدقّة الساعة/رجوعها/
  التطبيع). بدل كده في **3 أعمدة صريحة** على `deleted_conversations`:
  - `witness_origin` — `'attempt'` لو شاهد أنشأته محاولة حذف بعيد، `NULL` لو شاهد قديم.
  - `witness_attempt_id` — رمز المحاولة المالكة (UUID hex) — مفتاح الـ compare-and-swap.
  - `witness_preexisting` — `1` لو الصف كان موجودًا **قبل** أول محاولة بعيد (شاهد قديم)،
    `0` لو أول محاولة أنشأته. القيمة **monotonic** (بتترقّى 0→1 بس) ⇒ إعادات المحاولة
    ما بتغيّرهاش. التصنيف دائم ⇒ ينجو من الانهيار/إعادة التشغيل.
  - **الترحيل:** عند فتح قاعدة قديمة، `_migrate` بتضيف الأعمدة (`ALTER TABLE`، غير مدمّر)
    وتوسم **كل** الصفوف الموجودة مسبقًا `witness_preexisting=1` (بالتعريف سابقة لأي محاولة).
    الترحيل idempotent وآمن عند الانقطاع (الـ ALTER + الـ UPDATE في نفس معاملة `_init_schema`).
- **الـ compare-and-swap (OHB2-PR6 — إصلاح سباق lost-update):** كل تغيير حالة بعد النداء
  البعيد بيتحوّل لـ CAS على `witness_attempt_id` (`revert_remote_deletion_cas` و
  `clear_witness_cas`، داخل `BEGIN IMMEDIATE`): محاولة قديمة **ما تقدرش** تطمس أو تحذف
  حالة/شاهد أثبتته محاولة أحدث (رد CAS فاشل ⇒ مفيش كتابة). تفاصيل مهمة:
  - **`'confirmed'` حالة نهائية:** كل CAS فيه شرط `remote_state != 'confirmed'` ⇒ مفيش أي
    عملية (حتى المالك الحالي) تقدر ترجّع أو تطمس أو تحذف شاهدًا مؤكّد الحذف بدليل إيجابي.
    التأكيد المتأخّر (`_finalize`) بيثبّت الحذف فعلًا، والـ CAS بيمنع أي تراجع بعده.
  - **المطابقة بـ `IS ?` مش `= ?`:** مالك الشاهد القديم بعد الترحيل `NULL`؛ `= NULL` ما
    بتطابقش أبدًا فكانت تسيب الصفوف القديمة المعلّقة عالقة للأبد — `IS ?` بتطابق `NULL`
    والقيم مع بعض (إصلاح انحدار مراجعة مستقلة).
  - مفيش قفل مكتوب بيُمسك عبر نداءات الشبكة (الوسم قبل النداء في معاملة قصيرة، والـ CAS
    بعده في معاملة قصيرة).
- **التسوية بعد إعادة التشغيل:** `bot.deletion.reconcile_pending_deletions` بتشتغل في إقلاع
  البوت: أي شات حالته `deleting`/`uncertain` بتتحقق من وجوده بعيدًا — غايب ⇒ تثبيت الحذف،
  موجود ⇒ رجوع محلي (بـ CAS على ملكية المحاولة)، تعذّر التحقق ⇒ يفضل معلّق (مفيش تخمين).
- **إعادة التفاعل الصريح (استثناء مقصود):** **زر «متابعة» (`watch`)** هو المسار الصريح الوحيد
  اللي بيشيل الشاهد ويبدأ دورة نظيفة (OHB2-C7). أما **إرسال برومت من الـ Mini App
  (`POST /conversations/{id}/prompt`) فمش إعادة تفاعل صريح** — أي برومت لشات اتحذف محليًا
  بيُرفض بـ **`409 conversation_deleted`**. السبب (OHB2-AUDIT-FIX-01): طلب برومت ممكن يبدأ
  **قبل** الحذف ويخلص **بعده** (await الشبكة/الضغط المزدوج/إعادة المحاولة)؛ لو سمحنا له بالإحياء،
  العملية المتأخّرة بتحيي شات اتحذف.
- **حد الإشعار (صريح):** إشعار تيليجرام **بدأ إرساله فعلًا قبل** الحذف ممكن يفضل يوصل
  (إشعار «طاير» — residual موثّق)؛ أما أي عمل يتعالج **بعد** كتابة الشاهد فمابيتسلّمش
  ومابيعملش متابعة/إكمال جديد.
- **تغطية:** `tests/test_remote_deletion.py` (التنسيق/الفشل/التسوية) +
  `tests/test_remote_deletion_witness_identity.py` (الترحيل/استقلال التصنيف عن الوقت/سباق
  lost-update/دورة الحياة) + `tests/test_conversation_deletion.py` +
  `tests/test_openhands_client.py` (بايثون) و`tests/frontend/delete.test.js` (واجهة).

## 13ب. صندوق الإشعارات (OHB2-08-05)

> المرجع الشامل لمنظومة الإشعارات (البنية، القاعدة، الموثوقية، عقد الـ API، الواجهة،
> التشغيل، والتحقّق) في `docs/NOTIFICATIONS.md`. القسم ده ملخّص الواجهة بالعربي.

سجل **متين (event-first / write-ahead)** للإشعارات: الحدث بيتسجّل في الصندوق **قبل** أي
إرسال على تيليجرام، فمايتفقدش لو الإرسال فشل أو العملية وقعت. المستخدم يرجع يشوف الإشعارات
من الـ Mini App حتى بعد ما الرسالة تتوه في شات تيليجرام.

- الجدول `notification_inbox` (في `bot/db.py`): `id` (PK)، `conversation_id`، `title`،
  `kind`، `message`، `created_at`، `read_at` (NULL = غير مقروء)، `event_key` (هوية الحدث)،
  وحالة التسليم المتينة: `delivery_status` (`pending`/`delivered`/`failed`)،
  `delivery_attempts`، `last_attempt_at`، `delivered_at`، `last_error`، `next_retry_at`،
  `chat_id`، و`transition_status` (الحالة المرصودة عند إنشاء الحدث — **وصفية** للعرض)
  و`transition_seq` (رقم عصر الانتقال = **الهوية** الموحّدة بين العاملين، Batch 3R-FIX2)،
  و`claim_token`/`claim_at` (حجز ذرّي بمدة صلاحية لمحاولة تسليم جارية — Batch 3R-FIX2-F1).
  **إضافي** — بيتعمل بـ `CREATE TABLE IF NOT EXISTS` والترحيل
  بيضيف الأعمدة الجديدة لـ `ALTER TABLE`، فالقواعد القديمة بتاخدها تلقائيًا من غير فقد بيانات.
- **الحدث أولًا (write-ahead)**: الحدث بيتسجّل `pending` عند **لحظة اكتشاف** الانتقال،
  **قبل** أي إرسال (في المراقب `_record_event`/`_notify`/`_deliver` والمُبلّغ
  `_record_inbox_event`). بعد الإرسال بيتحدّث: `delivered` عند النجاح، أو `delivery_attempts++`
  مع `next_retry_at` عند فشل مؤقّت/`RetryAfter`، أو `failed` عند استنفاد الميزانية. كده
  مفيش فقد حدث لو تيليجرام فشل أو العملية وقعت. الكتابة معزولة: أي فشل في الصندوق ما
  يكسرش تسليم الإشعار (الإرسال يمشي، والحدث يبقى `pending` للاسترجاع).
- **الاسترجاع (recovery sweep)**: في بداية كل دورة، المراقب والمُبلّغ بيعيدوا محاولة الأحداث
  المعلّقة اللي **مش** مملوكة لمسار نشط (مش متابَعة دلوقتي، ومفيش عليها علامة `notifier_pending`
  جارية، ومش ظاهرة في نتائج البحث الحالية) — فحدث اتشالت متابعته بعد استنفاد المحاولات أو
  علّق عبر إعادة تشغيل لسه بيوصل. الأحداث المملوكة لمسار نشط بتتعامل في مكانها (مفيش إرسال مزدوج).
- **F-1 (Batch 3R-FIX2-F1): استرجاع الحدث النهائي العالق أثناء بقاء المتابعة**: لو المراقب
  اكتشف انتقالًا نهائيًا وتسليمه فشل (الحدث `pending`)، وبعدها اتسجّلت الحالة النهائية على صف
  المتابعة (`watched.last_state` بقى نهائي) — المسار النشط للمراقب مابيرجعش يحاول (شرط
  `is_terminal(state) and not is_terminal(w.last_state)` بقى False)، والمُبلّل كان يستثني
  المحادثة المتابَعة من الاسترجاع ⇒ الحدث يفضل `pending` للأبد لحد ما المتابعة تتشال.
  الإصلاح: المُبلّل بقى يسترجع **حدث الانتقال النهائي الحالي** للمحادثة المتابَعة **العالقة**
  (`_watched_event_stuck`: المتابعة موجودة + `last_state` نهائي + الحدث هو العصر
  الحالي). مفيش ازدواج: الأحداث غير المتابَعة بيفضل يتولّاها استرجاع المراقب، والمسار النشط
  للمتابعة غير العالقة بيفضل مالكها.
- **الحجز الذرّي (claim lease، Batch 3R-FIX2-F1)**: قبل أي إرسال استرجاعي، العامل بيحجز الصف
  ذرّيًا (`claim_pending_inbox`: `UPDATE ... WHERE id=? AND delivery_status='pending' AND
  (claim_token IS NULL OR claim_at<=cutoff)`) في معاملة `BEGIN IMMEDIATE` — فلو العاملين
  حاولوا نفس الحدث في نفس اللحظة واحد بس يبعت (آمن عبر اتصالات SQLite منفصلة، مفيش
  check-then-act). `claim_at` بيدّي الحجز **مدة صلاحية**: حجز قديم (من عملية وقعت قبل ما تحرّره)
  بيتخطّاه الاسترجاع تلقائيًا فمافيش حدث يعلق محجوزًا للأبد. الحجز بيتشال بعد كل محاولة
  (`record_inbox_attempt`/`mark_inbox_delivered`/`mark_inbox_failed`/`set_inbox_retry_deadline`).
  ده **مش** ضمان exactly-once: نافذة غموض تيليجرام (قبول الرسالة قبل تسجيل التسليم) لسه موجودة
  ومقصودة — بنفضّل استرجاع آمن وعدم يقين صريح على فقد إشعار بصمت.
- `kind` ∈ `terminal` (شات متابَع انتهى) / `timeout` (مهلة 24 ساعة) / `missing` (شات
  مفقود) / `stale_report` (مفيش تقرير جديد) / `proactive` (إشعار عام من المُبلّغ).
- **الهوية المنطقية للحدث (idempotency)** — هوية **دائمة** مش مبنية على نص الحالة:
  - المراقب: `conversation_id | kind | watch_seq | last_state` (`watch_seq` معرّف دائم
    وفريد لكل دورة متابعة).
  - المُبلّغ: `conversation_id | proactive | transition_seq`، حيث `transition_seq` = **رقم
    عصر الاكتشاف** الدائم في `notification_state`: يزيد **مرة واحدة عند اكتشاف** انتقال
    حالة نهائية جديد (`note_transition`، مش عند التسليم)، ويثبت خلال كل إعادات المحاولة
    لنفس الانتقال. كده `finished→running→finished` بيدّي رقمين مختلفين ⇒ حدثين منفصلين
    (مفيش حجب لإشعار تكرار)، وإعادة الاستطلاع/إعادة التشغيل لنفس الانتقال بتعيد نفس الرقم
    (مفيش تكرار).
  - قيد تفرّد **جزئي** على القاعدة (`idx_inbox_event_key ... WHERE event_key IS NOT NULL`)
    بيمنع تسجيل نفس الحدث مرتين (retry / restart / reconcile) — الحماية على مستوى القاعدة
    مش الذاكرة. الصفوف القديمة (event_key = NULL) ما بتتأثّرش بالقيد، وإعادة المتابعة
    (`watch_seq` جديد) بتعتبر حدث جديد (سجل منفصل، مش ازدواج).
- **هوية الانتقال الموحّدة عبر العاملين (Batch 3R-FIX2)**: المراقب والمُبلّل بيسجّلوا **نفس
  رقم عصر الانتقال** (`transition_seq` من `note_transition`) لنفس الانتقال — مش وصف الحالة.
  وفيه قيد تفرّد **جزئي** إضافي
  (`idx_inbox_transition_seq_unique ON (conversation_id, transition_seq) WHERE transition_seq
  IS NOT NULL AND delivery_status='pending'`). فلو الاتنين لقوا نفس الانتقال (مثلاً المراقب
  استنفد المحاولات والمُبلّل لسه شايفه)، التاني بياخد `None` من `add_inbox_event` ⇒
  **مفيش صف منافس ومفيش رسالة تانية** لنفس الانتقال. اللي بيوصل الحدث (عبر مساره أو
  الاسترجاع) بيسجّل الانتقال "مُبلّغ" عبر `record_notification_sent` عشان التاني ما يبعتهوش.
  القيد **معلّق بس** (`pending`) فصف `failed` ما يمنعش انتقالًا جديدًا حقيقيًا لنفس الحالة.
  **إصلاح Batch 3R-FIX2**: الهوية كانت قبل كده على `transition_status` (وصف الحالة)، وده كان
  بيحجب انتقالًا حقيقيًا تاني بنفس الحالة (مثلاً `finished` معلّق ثم `finished` جديد) — بقى
  على رقم العصر، فكل انتقال حقيقي بياخد رقمًا مختلفًا وحدثًا منفصلًا.
- **`notifier_pending` مربوط بالحدث**: علامة التسليم المعلّق الدائمة بتحمل `event_id` +
  `transition_seq`، فالتسوية بعد إعادة التشغيل بتعلّم **نفس** حدث الصندوق `delivered`
  (ذرّيًا، `BEGIN IMMEDIATE`) — مفيش حدث معلّق للأبد. (Batch 3R-FIX2: `transition_seq` بقى
  **عصر اكتشاف** بيتثبّت عند الاكتشاف في `note_transition`، فالتسوية ما بتلمسوش.)
- **حدود payload ونمو محدود**: الرسالة بتتقصّ عند `INBOX_MAX_MESSAGE_CHARS` (1000).
  التقليم عند الإدراج (نفس المعاملة) بسياسة صريحة (Batch 3R-FIX): **الصفوف المعلّقة
  (`pending`) وغير المقروءة (`read_at IS NULL`) مايتقلّمش أبدًا**؛ **المقروءة بس** مؤهّلة
  للتقليم الأقدم أولًا لحد `INBOX_MAX_PER_CONVERSATION` (50) لكل محادثة و`INBOX_MAX_TOTAL`
  (500) عامًا — والسقفين **سقفان ناعمان**: لو الصفوف المحمية لوحدها تعدّيهم، الجدول يتعدّاهم
  (مفيش حذف صامت لإشعار لسه ما شافهوش المستخدم). القايمة بترقيم على مستوى SQL
  (`INBOX_PAGE_SIZE = 10`) بترتيب `id DESC` (مستقر لأن الـ id تسلسلي). `unread_count` بيرجع
  مع كل صفحة ومع `bootstrap` لشارة التبويب.
- **الترحيل**: الأعمدة الجديدة (`event_key`، `delivery_status`، `delivery_attempts`، ...
  و`transition_status`، و`transition_seq` في `notification_inbox`) و`transition_seq` +
  `discovered_status` في `notification_state` بتتضاف لقاعدة موجودة عبر
  `ALTER TABLE ... ADD COLUMN` في `_migrate`، والفهارس الفريدة الجزئية (`idx_inbox_event_key`
  و`idx_inbox_transition_seq_unique`) بتتعمل **بعد** ضمان الأعمدة (نمط المستودع) — idempotent وآمن
  عند تكرار الفتح. الفهرس القديم `idx_inbox_transition_unique` (على `transition_status`) بيتشال
  عند الفتح (فهرس بس — مفيش مساس بالبيانات). جداول Batch 1/2 (`watched`/`notification_state`/
  `outbox`/`notifier_pending`/`notifier_retry_not_before`) ما بتتلمسش غير إضافة الأعمدة الإضافية.
- الواجهة: تبويب **الإشعارات** بشارة غير المقروء، قايمة، تعليم عند الضغط (وبيفتح الشات)،
  شارة حالة التسليم (`بيتسلّم…`/`فشل التسليم`)، وزر **تعليم الكل كمقروء**.
- **API**: `GET /api/v1/notifications?page=&unread=1`، `POST /api/v1/notifications/{id}/read`،
  `POST /api/v1/notifications/read-all`. الـ DTO ما بيكشفش `event_key` (حمولة داخلية)، وبيحمّل
  `delivery_status`/`delivery_attempts`/`delivered_at`، وبيترقّم بترقيم محدود، والصفحة
  الفاضية بسبب تجاوز الحد بترجع للأولى.

## 14. اللي فاضل لمهام OHB2 اللاحقة

- جلسات **ثابتة عبر إعادة التشغيل** (المخزن الحالي في الذاكرة ⇒ أي restart بيلغي الجلسات).
- تصدير الشات **لسه في البوت بس** (مش معروض في الـ Mini App). أما الملفات والتكلفة فبقوا معروضين
  في تفاصيل الشات بعد استرجاع الميزات (F-08، القرار A — `DEFERRED_FEATURES_HIDDEN=False`).
- نسخ الرد الكامل لسه مش معروض في الـ Mini App.
- صندوق الإشعارات: **مفيش حذف/أرشفة** من الواجهة (التقليم تلقائي عند الحدود)، ولا فلترة
  "غير المقروء فقط" في الواجهة (الـ API بيدعم `unread=1`)، ولا إشعارات "مقروءة جزئيًا" —
  لو مطلوب نضيفه لاحقًا. **مفيش cleanup worker**: التقليم جوه نفس معاملة الإدراج.
- تفعيل `MINI_APP_ENABLED` في الإنتاج + تحديث `/app` يشاور على الواجهة الفعلية.
- معالجة الرابط الثابت (القسم 13).
