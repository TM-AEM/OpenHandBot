## 1) السياق والسلوك الحالي المُتحقَّق منه

OpenHandBot بوت تيليجرام **عملية واحدة** بتعمل long polling على تيليجرام، وقاعدة
SQLite **واحدة** بملك واحد. المسارات الثلاثة المميّزة للأمان (صندوق صادر، طلبات إنشاء،
ديدَب التحديثات) موجودة ومُختبرة. هذا الـ ADR بيسأل سؤالًا **واحدًا**: هل ربط
**نتائج معالجة التحديثات الدائمة** بتقدّم `getUpdates` offset المرفوع فعلًا لتيليجرام
ممكن بأمان، وإزاي؟

## 2) المشكلة الفعلية للموثوقية

المشكلة **مش** «فقد بيانات» مباشر. المشكلة إن **فيه ثلاث طبقات مختلفة بيتعاملوا
كأنهم حاجة واحدة**، وواحدة بس منهم بتتحكّم في إقرار تيليجرام:

1. **إقرار تيليجرام (خادم):** تحديث يتّعد **مؤكَّدًا** لما نداء `getUpdates` لاحق
   يستخدم `offset > update_id`. [F — توثيق Bot API + `_updater.py`]
2. **تقدّم offset في PTB:** بيحصل **لحظة الطابور** (`update_queue.put`)، **قبل** أي
   تنفيذ للـ handler. [F — `_updater.py:363-366`]
3. **الكشف الدائم في التطبيق (`processed_updates`):** بيسجّل «اتعالج» **ذرّيًا مع العمل
   الدائم**، وبيمنع ازدواج. [F — `bot/db.py`، `dedupe_update`]
4. **اكتمال معاملة العمل الدائم (`commit`).** [F]

**النتيجة الحاسمة [F]:** في الإعداد الحالي، **إقرار تيليجرام (1) بيتحدّد بتقدّم offset
في PTB (2)، واللي بيحصل عند السحب/الطابور — أي قبل التنفيذ.** يعني تيليجرام بيعتبر
التحديث **مقروءًا** قبل ما الـ handler يشتغل أصلًا. آلية الإقرار المحلي (3/4) —
`commit_batch_outcomes`/`get_acknowledgment_boundary`/`settings.acknowledgment_boundary`
— **مابتدخّلش ولا بتتحكّم في (1) أو (2)**؛ هي **سجل حالة داخلي** فقط. [F — F8 + grep]

فالمشكلة اللي الـ ADR بيعالجها: **إزاي نوصل نتيجة المعالجة الدائمة (3/4) بتقدّم offset
الحقيقي (1/2) بأمان، من غير كسر المعمارية المعتمدة (عملية واحدة، مالك قاعدة واحد،
مفيش poller تاني، مفيش مخزن جديد).**

### 3.2 الحقائق الحاكمة [F]

- **متى يتقدّم offset:** عند `update_queue.put` لكل التحديثات المجلوبة، **قبل** أي
  تنفيذ. `_last_update_id = updates[-1].update_id + 1`. [F — `_updater.py:366`]
- **متى يتحقّق الإقرار عند تيليجرام:** نداء `getUpdates` التالي بيحمل
  `offset = _last_update_id` (أي `last_seen+1`) ⇒ كل التحديثات ≤ `last_seen`
  **مؤكَّدة**. [F]
- **هل `concurrent_updates` بتأثّر؟** [F — F2] أيوه: 256 مهمة معالجة **مستقلة**
  (`create_task` بدون `await`) ⇒ إتمامها **مش مرتّب**. التحديثات بتتسحب **مرتّبة**،
  و`dedupe_update` (group=-1) بتتنفّذ لكل تحديث، لكن **اكتمال العمل الدائم مش مرتّب**.
  بالتالي أي فكرة «حدّ إقرار = أطول بادئة مكتملة بالترتيب» **غير قابلة للتحقّق بدون
  تسلسل**، لأن الاكتمال بيحصل out-of-order. [F — `_application.py:1221-1225`]
- **استثناءات الـ handler:** PTB بيمرّرها لـ `process_error` (معالجنا بيسجّل فشل بثبات)
  وبعدين **يرجّع عاديًّا** ⇒ رجوع `process_update` **مش** دليل نجاح. [F — F12]
- **هل التطبيق الحالي يقدر يمنع PTB من الإقرار قبل المعالجة الدائمة؟** **لأ.**
  `_last_update_id` **خاص بـ Updater ومش مكشوف للـ Application**، ومابيتغيّرش بناءً على
  نتيجة الـ handler. [F — لا واجهة ربط + `_updater.py:366`]
- **`drop_pending_updates=True` بتعمل إيه فعليًا؟** بتندَه مرّة في بداية `_network_loop`
  عبر `_bootstrap` ⇒ `delete_webhook(drop_pending_updates=True)` ⇒ تيليجرام **بيمسح
  التحديثات المعلّقة** على الخادم قبل الاستطلاع. [F — F11] (نتيجة تشغيلية: أوامر اتبعتت
  والبوت واقف **بتترمي** — مقصود، `main.py:62-66`.)
- **هل الإقرار المحلي بيتحكّم في offset الحقيقي؟** **لأ.** `commit_batch_outcomes`
  بتكتب `settings.acknowledgment_boundary` بس؛ **مفيش مستدعي** بيقراه ويغيّر offset
  الاستطلاع. [F — F8]

### 3.3 التمييز الإلزامي بين الأحداث (غير متكافئة) [F]

| الحدث | الإشارة في الكود | بيعني إيه |
|-------|------------------|-----------|
| اتسحبت من تيليجرام | رجوع `get_updates` | وصلت للذاكرة بس |
| اتحطّت في طابور PTB | `update_queue.put` | **offset اتقدّم هنا** |
| اتبعتت لـ handler | `create_task`/`await process_update` | بدأ التنفيذ |
| الـ handler رجع | رجوع الدالة | **مش** دليل نجاح (استثناءات مبلوعة) |
| العمل الدائم اتـcommit | `commit()` في `add_or_group_outbox`/`add_creation_job`/`toggle_*` | دليل دائم |
| مؤهّل محليًا للإقرار | `processed_updates.outcome ∈ _ACK_ELIGIBLE` | سجل داخلي بس |
| تيليجرام استلم offset أعلى | `getUpdates(offset=last+1)` نجح | الإقرار الفعلي |

### 4.1 ملاحظات على المصفوفة

- **الخطر الجوهري** (سيناريوهات 1، 2، 13): تحديث اتسحب واتحط في الطابور ⇒ **offset
  اتقدّم** ⇒ تيليجرام خلاص بيعتبره مقروءًا، وقبل ما الـ handler ينفّذ، أي انهيار/فشل
  **دايم** = **فقد فعلي** بلا تعافٍ. [F]
- **الاستثناء الحاسم:** العمليات الذرّية (outbox/creation/toggle) بتسجّل «معالَج» **في
  نفس المعاملة** ⇒ **مفيش** سيناريو «سجل ديدَب موجود والعمل ناقص» (17). [F — `dedupe_update` docstring + `db.add_or_group_outbox`]

  الدائم **غير قابلة للحساب لحظيًّا** بالترتيب. [F — F2]
- **مفيش ادّعاء exactly-once.** ده **كشف تكرار محدود** + احتمالات فقد/تكرار موثّقة.

## 5) خيارات المعمار

### الخيار A — مستهلك `getUpdates` مخصّص (داخل نفس العملية)

حلقة استطلاع **داخل العملية الواحدة** بتستدعي `bot.get_updates(offset=...)` بنفسها،
وبتتحكّم في الـ offset بناءً على **حدّ النتائج الدائمة المُـcommit**، وبتغذّي
`application.update_queue` بالـ dispatch العادي.

- **آلية مقترحة [A]:** نبني `Application` بـ `updater(None)` (مُتحقَّق: مدعوم في 22.8
  ويحافظ على `update_queue` + `_update_fetcher`) ⇒ بعدين حلقة مخصّصة:
  1. `updates = await bot.get_updates(offset=next_offset, timeout=...)`
  2. `next_offset = updates[-1].update_id + 1` **مؤقتًا في الذاكرة** (بدون إرساله لتيليجرام فورًا)
  3. لكل تحديث: `await update_queue.put(u)` ثم **انتظر اكتمال الـ processing** (تسلسل)
  4. بعد كل تحديث: ثبّت نتيجته (نفس معاملة العمل)، احسب البادئة المؤهّلة، وخزّن الحدّ
  5. **النداء التالي** بـ `offset = boundary + 1` (أو `last_seen+1` لو كلهم مؤهّلين)
  ⇒ الإقرار الفعلي عند تيليجرام **بيحصل فقط** لما `boundary+1 > update_id`.

| معيار | تقييم |
|-------|-------|
| صحة الإقرار | **عالية** — offset مرتبط بالبادئة المؤهّلة فعليًا |
| سلوك الانهيار/إعادة التشغيل | حدّ محفوظ في `settings`؛ الاستئناف من `boundary+1` |
| ترتيب التحديثات | **مضمون** (تسلسل إجباري) |
| التعامل مع الفشل | الحدّ يتوقف عند أول غير مؤهّل (fail-closed) |
| poison-update | يحجز الإقرار؛ يحتاج تسوية يدوية (§8) |
| التكرار/الديدَب | نفس `dedupe_update` + الحدّ يمنع إعادة التسليم أصلًا |
| حدود معاملات SQLite | كما هي (نفس الملك/المعاملة الذرّية) |
| التوافق مع الـ handlers | **كامل** (نفس `update_queue`/نفس المعالجات) |
| التعقيد | **متوسط-عالي**: حلقة جديدة + تسلسل + إدارة offset + تسوية الإغلاق |
| القابلية للاختبار | **عالية** (نقدر نحاكي `get_updates` ونراقب قيم offset) |
| التعافي التشغيلي | جيد (حدّ محفوظ + سجلات فشل) |
| مخاطر فقد/تكرار | **أقلها** — لكن **لسه مفيش exactly-once** (تكرار ممكن لو إعادة التسليم بعد تسوية) |
| مخالفة القيود (§7) | **لأ** (عملية واحدة، مالك واحد، **مفيش** poller متوازي مع Updater لأننا نلغي Updater) |

### الخيار B — بديل متوافق مع PTB

نخلّي `Updater` بتاع PTB شغّال، لكن نمنع offset إنه يتقدّم **بعد** الحدّ الدائم المؤهّل.

- **الفكرة [A]:** نلفّ/نعترض `Bot.get_updates` (subclass أو `get_updates_request`) عشان
  نضبط `offset` من الحدّ المؤهّل، ونؤجّل «التأكيد» لحد ما الحدّ يتقدّم.
- **العقبة الحاسمة [F]:** `Updater` بيدفع `_last_update_id` **جوّيًا** بعد الطابور
  (`_updater.py:366`) ولا فيه خطّاف رسمي للتأثير في ده. أي «منع» محتاج **تعديل داخلي في
  سلوك PTB** (monkeypatch/patch) — ده **هشّ** وبيكسر مع ترقيات PTB، وقد يخلق poller
  فعليًا متوازي مع منطق مكرّر.
- **مخالفة القيود:** قد يقترب من «poller تاني»/«منطق استطلاع مزدوج» لو عوّضنا التأجيل
  بحلقة خاصة ⇒ **يتعارض مع §7**.

| معيار | تقييم |
|-------|-------|
| صحة الإقرار | متوسطة — تعتمد على اعتراض داخلي هشّ |
| الانهيار/إعادة التشغيل | غير مضمون (offset جوّي في Updater) |
| الترتيب | مش مضمون (concurrent_updates) |
| الفشل/poison | صعب ضبطه بدون تسلسل |
| التوافق مع PTB | **هشّ** (اعتماد على تفاصيل داخلية) |
| التعقيد/الصيانة | **عالي + خطر كسر ترقيات** |
| القابلية للاختبار | منخفضة-متوسطة |
| القيود (§7) | **خطر مخالفة** |

### الخيار C — PTB الحالي مع تتبّع محلي فقط (الوضع الراهن + الأدوات الموجودة)

تسيب `run_polling` زي ما هو، وتستخدم `processed_updates`/`update_failures`/
`acknowledgment_boundary` **كسجل داخلي بس**.

| معيار | تقييم |
|-------|-------|
| صحة الإقرار | **صفر تحكّم** في إقرار تيليجرام (بيحصل عند الطابور) [F] |
| الانهيار/إعادة التشغيل | offset الحقيقي مش محفوظ؛ `drop_pending_updates` يمسح المعلّق |
| الترتيب | مش مرتّب (concurrent) |
| الفشل/poison | يُسجَّل بثبات لكن **مايحجبش** إقرار تيليجرام |
| التعقيد | **أقلها** |
| مخاطر فقد | **أعلاها** (سيناريوهات 1/2/13) |

**الحكم على C:** **مابيوفّرش** ربط النتيجة الدائمة بالإقرار الفعلي؛ «الحدّ المحلي»
**مش** إقرار تيليجرام (بلا دليل ربط). فمابيحقّقش هدف الـ ADR، لكنه **مقبول** لو
متطلبات الموثوقية الفعلية ضعيفة (استخدام فردي؛ انظر §6).

## 6) التوصية

**التوصية: الخيار A** (مستهلك `getUpdates` مخصّص داخل نفس العملية، مع `updater(None)`)،
**بشرط** إجماع على متطلبات الموثوقية والمخاطر المقبولة، وبعد **موافقة صريحة منفصلة**.

**الأساس:**
1. هو **الوحيد** اللي بيوصّل النتيجة الدائمة بتقدّم offset الحقيقي **فعليًا** (§3).
2. بيحافظ على **كل** قيود §7 (عملية واحدة، مالك قاعدة واحد، **مفيش** poller متوازي،
   مفيش مخزن/جدول/worker جديد، مفيش replay تلقائي لآثار OpenHands الغامضة).
3. قابل للاختبار (نقدر نحاكي `get_updates` ونراقب قيم offset بالظبط — §13).
4. بيحوّل «الفقد المحتمل» (سيناريوهات 1/2/13) لإعادة تسليم **متحكَّم فيها** بدل ضياع.

**لماذا مش B:** اعتراض داخلي هشّ + خطر كسر ترقيات + اقتراب من «poller تاني» (§7).

**لماذا مش C كحلّ:** مابيوفّرش أي تحكّم حقيقي في الإقرار [F].

**⚠️ [G] فجوة أدلة قبل التنفيذ:** لازم نحدّد **متطلبات الموثوقية الفعلية**: هل ضياع
تحديث واحد نادر مقبول (استخدام فردي) ولا لأ؟ لو مقبول ⇒ C ممكن يكفي (أقل تعقيدًا).
الـ ADR **ميوصيش بالتنفيذ** قبل حسم ده.

## 7) دورة حياة التحديث ونموذج انتقال الحالة المقترح [A]

```
FETCHED (getUpdates رجّع الدفعة؛ offset لم يُرسَل بعد)
   │  put في update_queue + تسلسل التنفيذ
   ▼
DISPATCHED (بدأ handler؛ dedupe_update اتنفّذت)
   │
   ├─► DUPLICATE  ⇒ ApplicationHandlerStop ⇒ outcome=duplicate_completed (مؤهّل)
   │
   ├─► DURABLE_DONE   ⇒ outcome ∈ {durable_completed, durable_intent_recorded} (مؤهّل)
   │
   ├─► IGNORED        ⇒ outcome=explicitly_ignored (مؤهّل)
   │
   └─► FAILED
         ├─ transient (BUSY/LOCKED/شبكة) ⇒ failed_transient (غير مؤهّل، قابل لإعادة محاولة)
         └─ permanent / unknown          ⇒ failed_permanent | partial_or_unknown (غير مؤهّل، poison)
```
**قاعدة الانتقال:** الحدّ المؤهّل = أطول **بادئة** بترتيب الاستقبال كل نتائجها مؤهّلة.
أول غير مؤهّل **بيحجز** كل اللي بعده. [A — مطابق لـ `acknowledgment_boundary` الحالي]

## 8) قواعد ترتيب الدفعة والبادئة المؤهّلة الأطول [A]

1. الدفعة بتتسحب **مرتّبة** بترتيب تيليجرام؛ بنحافظ على **نفس الترتيب**.
2. التنفيذ **متسلسل** (مهم لـ A) ⇒ «البادئة المكتملة» قابلة للحساب لحظيًّا.
3. الحدّ = `last update_id` في أطول بادئة مؤهّلة (فجوات `update_id` مسموحة).
4. **مش** `max(update_id)+1`: نجاح لاحق **مش** بيكسر حجز فشل سابق.
5. الإقرار الفعلي = `getUpdates(offset = boundary+1)`.
6. لو **أول** تحديث غير مؤهّل ⇒ `boundary=None` ⇒ **مفيش تقدّم** للإقرار (حتى لو
   اللي بعده نجح) ⇒ head-of-line blocking (مقصود، fail-closed).

## 9) دلالات الانهيار/إعادة التشغيل [A]

- **الحدّ المؤهّل** يتحفظ في `settings` (نفس `ACK_BOUNDARY_KEY`) **ذرّيًا** مع نتائج الدفعة.
- **عند الإقلاع:** نستأنف الاستطلاع من `boundary+1` (لو موجود) بدل صفر؛ وكمان نراجع
  `processed_updates` للديدَب.
- **`drop_pending_updates`:** مقترح **مراجعته** (مش تغييره الآن): مع استئناف الحدّ،
  `drop_pending_updates=True` قد يمسح تحديثات **لم تُعالج** لكن الحدّ **مش** بيوصلها ⇒
  تعارض. القرار النهائي بند منفصل (§17).
- **ما بعد الانهيار قبل الطابور (سيناريو 1):** مع A، الـ offset **مايتقدّمش** عند
  السحب؛ التحديثات هتُسحب تاني (لأن تيليجرام لسه شايفها معلّقة) ⇒ **تعافٍ ممكن**.

## 10) سياسة الـ poison-update والتسوية اليدوية

**السياسة المقترحة (تنفيذ مؤجّل):**

1. **الكشف:** تحديث نتيجته `failed_permanent` أو `partial_or_unknown` (صف في
   `update_failures`).
2. **التمييز عن العابر:** `failed_transient` (BUSY/LOCKED/شبكة) يُعاد محدودًا؛
   `failed_permanent` قرار تشغيلي.
3. **التأثير على الإقرار:** الأول غير المؤهّل **بيحجز** البادئة ⇒ الإقرار **بيتوقف**
   عنده (مفيش تقدّم صامت).
4. **اكتشاف المشغّل:** صف واضح في `update_failures` + أمر تشخيص مقترح
   (`/updates_status` — عرض الحدّ + أول تحديث عالق + السبب؛ **بدون** محتوى حساس).
5. **الفحص والتسوية:** المشغّل يقدر يشوف التحديث العالق وسببه، ويقرّر يدويًا.
6. **منع التخطّي الصامت:** مفيش أي تجاوز تلقائي؛ الحدّ مايتقدّمش غير بعلاج صريح.
7. **التفويض اليدوي:** ممكن المشغّل **يصرّح** بتخطّي تحديث عالق (تعليمه `poison_acknowledged`
   مع سبب/وقت)، **وبعدها بس** يتقدّم الحدّ — قرار صريح مُوثَّق، مش صامت.
8. **الدليل الدائم:** صف `update_failures` (النوع + السبب + الوقت) + قرار التخطّي اليدوي.

> **مفيش تنفيذ لآلية تخطّي في هذا الـ ADR.**

## 11) آثار الديدَب والاحتفاظ

**مُتحقَّق منه [F]:**
- `PROCESSED_UPDATES_KEEP = 50_000` (سقف نافذة) — **لسه موجود** [F5].
- التقليم **عند الإقلاع بس** (`_post_init`) ⇒ **بيشيل أقدم الصفوف بغض النظر عن الإقرار**
  [F5]. فممكن يمسح سجل تحديث **لسه** ما اتأكّدش عند تيليجرام ⇒ إعادة تسليمه القديمة
  **ممكن تعيد التنفيذ** (اتأكّد ميكانيكيًا في تحقيق سابق؛ إعادة التسليم الإنتاجية
  **غير مُثبَتة**).
- **مفيش حدّ مونوتوني (watermark) منفصل** حاليًا غير `settings.acknowledgment_boundary`
  (مكتوب بس `commit_batch_outcomes` اللي مالهاش مستدعي) [F8].

**الآثار [A]:**
- **حدّ مونوتوني (watermark)** = `max(update_id)` المؤكَّد فعليًا. أي `update_id ≤ watermark`
  **مايتعالجش** حتى لو سجله اتقلّم ⇒ **يمنع** إعادة تنفيذ قديمة بعد التقليم.
- **إذن:** خيار A (اللي بيثبّت الحدّ **قبل** تقديم الإقرار) **هو اللي يخلّي الـ watermark
  موثوق** ⇒ التقليم الآمن يعتمد على **تثبيت الحدّ** (مش على نافذة الـ 50k لوحدها).
- **توصية:** الحدّ المونوتوني **مكمّل** للسجلات المحتفظ بها، **مش** بديل عنها (السجلات
  بتدّي تفاصيل النتيجة؛ الحدّ بيدّي ضمان «ما نرجعش لورا»).
- **مفيش تغيير احتفاظ في هذا الـ ADR** [F].

## 12) اعتبارات أمنية وتشغيلية

- **مفيش أسرار في سجلات الإقرار:** `update_failures` بتخزّن **النوع** بس (`type(exc).__name__`)
  — نتأكد إن ده يفضل كده (مفيش نص استثناء/محتوى رسالة).
- **مفيش وعد exactly-once** في أي رسالة للمستخدم.
- **fail-closed** في كل مسارات الفشل (dedupe، حارس القاعدة، الفشل الغامض) — مايتغيّرش.
- **سياسة الصندوق (sending/unknown)** — مايتغيّرش؛ مفيش replay تلقائي لآثار OpenHands الغامضة.
- **مالك قاعدة واحد:** خيار A **مايضيفش** أي poller متوازي (بيلغي Updater عبر
  `updater(None)`) ⇒ يفضل مالك واحد.
- **التشغيل:** أمر تشخيص للحدّ/التحديث العالق، ومفيش محتوى حساس في اللوج.

## 13) الاختبارات المطلوبة للتكامل والانحدار [A — مقترحة]

لو الخيار A اتوافق عليه:
1. **قيم offset الفعلية (مocked `get_updates`):** التأكد إن النداء التالي بيحمل
   `offset=boundary+1` بالظبط بعد بادئة كاملة، و`offset` **مايتقدّمش** عند أول غير مؤهّل.
2. **فشل أول/وسط/آخر تحديث في دفعة** ⇒ الحدّ يتوقف صح.
3. **البادئة المؤهّلة الأطول** (مغطّى جزئيًا في `test_manual_polling_outcome_and_ack.py`).
4. **حدود الانهيار/إعادة التشغيل:** استئناف من الحدّ المحفوظ + عدم إعادة تنفيذ قديم.
5. **تسليم مكرّر بعد التقليم** ⇒ الـ watermark يمنع التنفيذ التاني.
6. **فشل القاعدة (BUSY/LOCKED/دائم)** ⇒ fail-closed + الحدّ مايتقدّمش.
7. **dispatch متزامن** (لو فُعّل) ⇒ مايخلّيش الاكتمال out-of-order يفسد الحدّ.
8. **الإغلاق أثناء الاستطلاع** ⇒ مفيش تقدّم إقرار غير آمن.

| **O_submitted** | آخر `offset` **اتبعت** فعلًا في نداء `getUpdates` | `settings.ack_offset_submitted` **[مخطط منفصل]** | اتكتب **قبل** الإرسال ⇒ بعد انهيار: «اتبعت (أو كان هُيبعت)» |
| **O_confirmed** | آخر `offset` **نجح** نداء `getUpdates` بيه (استجابة وصلت) | `settings.ack_offset_confirmed` **[مخطط منفصل]** | نداء واحد على الأقل نجح بيه **قبل** الانهيار |
| **U_acked** | آخر `update_id` **مؤكَّد عند تيليجرام** | **مشتق** = `O_confirmed − 1` | **مستحيل نعرفه بشكل مؤكد في اللحظة** |

**حقائق حاسمة [F]:**
- تيليجرام بيعدّ التحديث **مؤكَّدًا** لما نداء `getUpdates` لاحق يستخدم `offset > update_id`.
  فالإقرار **فعلي** بس لما الاستجابة **تنجح**. [F]
- **`B_eligible` المحلي المُـcommit مش بيثبت** إن تيليجرام استلم/قبل الـ offset المقابل. [F]
- بعد انهيار **مفيش** واجهة بتقولنا آخر `offset` ناجح **بشكل مؤكد**؛ **مش** هنجتهد ونقول إننا
  نعرف `U_acked`. [F — `_last_update_id` خاص بـ Updater ومش بيتحفظ]
- **بعد انهيار نعرف:** `B_eligible` (المحلي)، و`O_submitted`/`O_confirmed` (لو كتبناهم
  بأمان). **مش نعرف** `U_acked` بيقين مطلق — **بس** التصميم **آمن** لو كل استئناف
  **يعيد الإرسال من `B_eligible+1`** (إعادة إرسال offset = آمن/idempotent: تيليجرام
  بيعتبره إقرار، ومابيرجّعش تحديثات أقل من الـ offset). [A]

### 18.2 دلالات إعادة التشغيل عبر حدود الانهيار

| الحدّ | اللي اتـcommit قبل الانهيار | الاستئناف | الأمان |
|-------|------------------------------|-----------|--------|
| بعد المعالجة وقبل تثبيت الحدّ | العمل الدائم ✅، الحدّ لسه على `B_prev` | إعادة تسليم من `B_prev+1` ⇒ `dedupe_update` بيشوف سجل العمل ⇒ `duplicate_completed` ⇒ الحدّ يتقدّم | **آمن** (ديدَب + العمل الذرّي) |
| بعد تثبيت الحدّ وقبل نداء `getUpdates` | الحدّ `B_eligible` ✅ | إعادة الإرسال من `B_eligible+1` | **آمن** (الإرسال idempotent) |
| أثناء نداء `getUpdates` | `O_submitted` اتكتب، النتيجة مجهولة | أعد الإرسال بنفس الـ offset (`B_eligible+1`) | **آمن** (مفيش إقرار زيادة) |
| تيليجرام قبل الطلب وقبل وصول الاستجابة | مجهول (يمكن تيليجرام أكّد) | أعد الإرسال؛ تيليجرام ممكن يرجّع فاضي | **آمن** — **مفيش إقرار زيادة** (الإقرار بيحصل عند تيليجرام بس لما نرسل offset أعلى، واللي إحنا مش بنرسله غير بعد تأكيد العمل) |

**الغموض غير القابل للتجنّب [A]:** مفيش ضمان إن نداء `getUpdates` وصل/نجح (شبكة). التصميم
**آمن** لأن: (1) الـ offset **مايتقدّمش** إلا بعد **عمل دائم مؤهّل**؛ (2) إعادة الإرسال
**idempotent**؛ (3) مفيش replay تلقائي لآثار OpenHands الغامضة (§7 قيود).

### 18.3 الخوارزمية الرسمية (pseudocode)

```
# ثوابت محلية
KEEP = PROCESSED_UPDATES_KEEP            # 50000 (موروث، مش هنغيّره)
TRANSIENT_RETRY_DELAYS = DEDUPE_RETRY_DELAYS   # (0.25, 0.5, 1.0) [F]

# ---- الإقلاع ----
def startup():
    db = open_authoritative_db()          # مالك واحد
    if not db.run_startup_maintenance():  # نفس الفحص الحالي [F]
        abort("database_integrity")       # مفيش polling
    B = db.get_setting(ACK_BOUNDARY_KEY)  # None لو أول مرة
    first_offset = (int(B) + 1) if B is not None else DROP_BOOTSTRAP_OFFSET   # §18.4
    return Poller(offset=first_offset, boundary=(int(B) if B else None))

# ---- الدورة (single loop) ----
async def run(self):
    while self.running:
        batch = await self.bot.get_updates(offset=self.next_offset, timeout=T, allowed_updates=None)
        if not batch:                     # دفعة فاضية ⇒ نعيد بنفس الـ offset
            continue
        await self.process_batch(batch)

async def process_batch(batch):
    # 1) تحقق الترتيب (فجوات مسموحة، تنازلي/مكرّر مرفوض)
    ids = [u.update_id for u in batch]
    if ids != sorted(ids) or len(set(ids)) != len(ids):
        log.error("دفعة تيليجرام بترتيب غير متزايد — لا تقدّم إقرار")
        return                            # نسيب الحدّ زي ما هو؛ إعادة السحب لاحقًا
    # 2) تجاهل اللي تحت الحدّ (stale)
    fresh = [u for u in batch if self.boundary is None or u.update_id > self.boundary]
    # 3) تنفيذ **متسلسل** (واحد واحد) + انتظار الاكتمال
    for u in fresh:
        if not self.running:
            break                         # إغلاق: نوقف؛ الـ offset مش هيتقدّم للي ما اتعالجش
        self.next_offset_candidate = u.update_id + 1
        outcome = await self.dispatch_and_wait(u)   # §18.5
        db.record_outcome(u.update_id, outcome)      # atomic مع العمل الدائم
        # 4) البادئة المؤهّلة الأطول بترتيب الاستقبال
        newB = db.compute_eligible_prefix(self.boundary, [x.update_id for x in fresh], outcomes_so_far)
        if newB is not None and (self.boundary is None or newB > self.boundary):
            self.boundary = newB
            db.set_setting(ACK_BOUNDARY_KEY, str(newB))   # persist ذرّي
    # 5) اختيار الـ offset الجاي (fail-closed: يتوقف عند أول غير مؤهّل)
    if self.boundary is not None:
        self.next_offset = self.boundary + 1     # مش max(update_id)+1
    else:
        self.next_offset = self.first_offset_this_session   # مايتقدّمش لو أول تحديث غير مؤهّل
    # 6) (اختياري §18.4) لو كل دفعة الإقلاع غير مؤهّلة ⇒ سياسة drop المحسوبة

def compute_eligible_prefix(prev_boundary, received_order, outcomes):
    # أطول بادئة كل عناصرها مؤهّلة، بترتيب الاستقبال
    boundary = prev_boundary
    for uid in received_order:
        if not is_ack_eligible(outcomes.get(uid)):
            break                # أول غير مؤهّل بيحجز كل اللي بعده (head-of-line)
        boundary = uid
    return boundary              # ممكن يفضل prev_boundary (مفيش تقدّم)

def dispatch_and_wait(u):
    await self.app.update_queue.put(u)
    await self.completion_barrier.wait(u.update_id)   # §18.5: ننتظر اكتمال المعالجة الفعلي
    return self.app.recorded_outcome(u.update_id)      # النتيجة المُسجَّلة بثبات
```

**حالات مُعالَجة:**
- **فجوات `update_id`:** مقبولة — الحدّ بيعتمد على **ترتيب الاستقبال** مش التسلسل الرقمي.
- **تحديث مكرّر:** `dedupe_update` ⇒ `duplicate_completed` (مؤهّل) ⇒ الحدّ يتقدّم (مفيش عمل تاني).
- **تحديث stale (< الحدّ):** بيتجاهل قبل أي تنفيذ (§18.7 watermark).
- **دفعة فاضية:** إعادة بنفس الـ offset (مفيش تقدّم).
- **أول إقلاع (مفيش حدّ):** يبدأ من `DROP_BOOTSTRAP_OFFSET` (§18.4).
- **دفعة فيها تحديث غير مؤهّل:** الحدّ **يتوقف** عنده.
- **تحديثات بعد أول غير مؤهّل:** **بتتنفّذ** (ممكن تنجح) بس **الحدّ مايتخطّهاش**؛ الإقرار
  بيتوقف عند أول غير مؤهّل.
- **تحذير:** **ممنوع** `max(update_id)+1` لو هيتخطّى تحديث سابق غير مؤهّل.

### 18.4 الإقلاع و`drop_pending_updates` (حلّ التعارض)

> **⚠️ تصحيح v3 (§25.1):** الترتيب المقترح تحت («`getUpdates` **قبل** أي `delete_webhook`»)
> **غير صالح** — تيليجرام **مابيسمحش** بـ `getUpdates` وقت وجود webhook فعّال. شوف **§25**
> للترتيب الصحيح (`deleteWebhook` **قبل** `getUpdates`). الباقي محفوظ كسجل v2.

**التعارض [F]:** `drop_pending_updates=True` بيخلّي تيليجرام **يمسح** المعلّق عند الإقلاع
(`delete_webhook(drop_pending_updates=True)`) ⇒ التحديثات اللي اتبعتت والبوت واقف **بتترمي**
(مفيش إعادة تسليم). في نفس الوقت، التصميم المقترح بيعتمد على **إعادة التسليم** لتعافي
الانهيار (لو الـ offset مااتقدّمش). الاتنين **متعارضين** لو طُبّقوا مع بعض.

**سياسة الإقلاع المقترحة [A] (بتعيد استخدام الفحص الحالي [F]):**

1. **لو مفيش حدّ محفوظ (أول إقلاع أو قاعدة فاضية):** التحديثات المعلّقة القديمة **مالهاش
   قيمة تشغيلية** (أوامر/رسائل قديمة). **مسموح** `drop_pending_updates=True` زي النهاردة
   [F] — إعادة استخدام السلوك الحالي. (يتماشى مع قرار OHB2-02.)
2. **لو فيه حدّ محفوظ `B` (بعد أول تشغيل ناجح):**
   - **الاستئناف من `B+1` أولًا** (`getUpdates(offset=B+1, timeout=0)`).
   - الاستجابة بترجّع أي تحديثات معلّقة `> B` **لسه عند تيليجرام** ⇒ تتسح لالعملية العادية
     ⇒ **تعافٍ** (بدون مسح).
   - **الاستجابة فاضية** ⇒ **مفيش** شيء معلّق فوق `B` (إما اتأكّد أو مفيش) ⇒ **بعدها بس**
     مسموح ننادي `drop_pending_updates=True` لمسح أي شيء **تحت `B`** (مش لازم بس مضرّش).
   - **ترتيب إلزامي:** `getUpdates(offset=B+1, timeout=0)` **قبل** أي `delete_webhook`.
     **[باطل — v3 §25: الترتيب الصحيح هو `deleteWebhook` أولًا ثم `getUpdates`.]**

**هل لازم سلوك الإقلاع الحالي يتغيّر؟**
- **آه، في الحالة (2) فقط:** الترتيب الحالي (`_bootstrap` بتعمل `delete_webhook` **قبل**
  أول `getUpdates`) **لازم يتغيّر** لتصميم A — لأن مسح المعلّق قبل الاستئناف بيمنع تعافي
  سيناريو 1. الحالة (1) (مفيش حدّ) **تفضل زي ما هي**.
- **ملاحظة:** `drop_pending_updates` حاليًا بند في `run_polling` ([F] `main.py:67`).
  تصميم A **بيلغي Updater** ⇒ بقى **بند إقلاع صريح** في الحلقة المخصّصة (مش باراميتر
  `run_polling`). ده **تغيير سلوكي محتاج موافقة** (§17).
- **بديل أبسط (لو رفضنا التغيير):** سيب `drop_pending_updates=True` كما هو (زي الحالة 1)
  ⇒ **نتقبّل** إن تحديثات وقت التوقف بتترمي **وإن سيناريو 1 يفضل فقد** — يعني A مش
  بيحقّق مكسب التعافي الكامل. **قرار صريح مطلوب.** [G]

### 18.5 دورة حياة PTB والإغلاق

- **التهيئة:** `Application.builder()....updater(None).build()` — مُتحقَّق إنها بتشتغل في
  22.8 وبتسييب `update_queue` + منطق dispatch شغّال، **بس مفيش Updater** (فمفيش سحب
  تلقائي، ومفيش `_last_update_id` داخلي). [F — §5 الخيار A]
- **الحلقة المخصّصة الواحدة** بتملأ `application.update_queue` بنفسها؛ `Application._update_fetcher`
  **لسه شغّال** (بيتولّد في `start()`) وبياخد من الطابور ويوزّع على نفس الـ handlers. [F]
- **التسلسل الإجباري:** الحلقة بتستدعي `await update_queue.put(u)` ثم **تنتظر إشارة اكتمال**
  قبل التالي. (بديل: `concurrent_updates(1)` بس ده **مش كفاية** لأن `_update_fetcher`
  بياخد من الطابور أسرع من التنفيذ؛ فالتسلسل لازم يكون **في الحلقة المخصّصة**.)
- **مراقبة اكتمال المعالجة رغم ابتلاع PTB للاستثناءات [F]:** ماينفعش نعتمد على رجوع
  `process_update`. الطريقة: `dispatch_and_wait` **بتلفّ الـ handler نفسه** (wrapper) أو
  بتستخدم `application.create_task` مع **إشارة اكتمال** (`asyncio.Event` لكل `update_id`)
  بتتحط في `finally` للـ wrapper ⇒ «اكتمل» = «الـ wrapper خلص» (نجاح **أو** فشل مُسجَّل).
  النتيجة الحاسمة بتتقرأ من **القاعدة** (`processed_updates.outcome` / `update_failures`)،
  **مش** من رجوع الدالة. ⇒ **وضع التحديث في الطابور مش دليل نجاح** (متفق مع §3.3).
- **الإغلاق:** الحلقة بتقف على `running=False`؛ **بتوقف عن السحب فورًا**؛ التحديث الجاري
  **بيخلّص** (بننتظر إشارته) قبل ما نقفل. **الـ offset مايتقدّمش** لأي تحديث لسه ما اتعالجش.
- **SIGTERM:** بنسجّل `loop.add_signal_handler(SIGTERM, ...)` (نفس آلية PTB على غير ويندوز
  [F]) بيحدّد `running=False` وبيوقظ الحلقة (النداء الطويل بيتقاطع). بعد الحلقة: إغلاق
  نظيف (commit/checkpoint للـ WAL زي الموجود).
- **الطابور المعلّق عند الإغلاق:** **مش بنمسحه** — بنسيب التحديثات اللي ما اتعالجتش **عند
  تيليجرام** (بما إن الـ offset مااتقدّمش عليها) ⇒ إعادة تسليم عند الإقلاع ⇒ تعافٍ.
- **منع إقرار عمل اتطابور بس ما اكتملش:** الإقرار = تقدّم `offset`، واللي **بيحصل بس**
  بعد ما الحدّ يتقدّم، والحدّ **بيتقدّم بس** بعد `dispatch_and_wait` (اكتمال فعلي) +
  تسجيل نتيجة. ⇒ **مستحيل** نأكّد عمل مُطابور بس.

### 18.6 سياسة الـ poison-update التشغيلية

- **العابر vs الدائم:** العابر = SQLite BUSY/LOCKED أو فشل شبكة مؤقّت ⇒ `failed_transient`
  (قابل لإعادة محاولة). الدائم = أي حاجة تانية (برمجي/رفض غير متوقّع/استنفد المحاولات) ⇒
  `failed_permanent`؛ الغامض ⇒ `partial_or_unknown`. (نفس `classify_failure`/`_classify_failure`
  القائمين [F].)
- **إعادة المحاولة:** العابر **جوّه الـ handler** محدود بـ `DEDUPE_RETRY_DELAYS` (0.25/0.5/1.0)
  [F]. **مفيش** إعادة محاولة على مستوى الحلقة لغير العابر (مفيش تلقائي لتفادي replay).
- **العرض للمشغّل:** صف في `update_failures` (النوع + السبب + الوقت) + أمر تشخيص مقترح
  `/updates_status` — بيعرض **الحدّ** + **أول تحديث عالق** (النوع/السبب/الوقت) + عدد الصفوف
  العالقة. **بدون** محتوى رسالة (مفيش نص رسالة مخزّن أصلًا [F]).
- **الفحص بدون كشف محتوى حساس:** نعرض `update_id`/`outcome`/`reason`(نوع الاستثناء)/الوقت بس.
- **الأفعال المسموحة:** (أ) **إعادة محاولة يدوية** للتحديث العالق (آمنة للعابر)؛ (ب)
  **تجاوز مصرَّح به** (skip) — **قرار صريح مُوثَّق**، **مش** تلقائي.
- **التوثيق الدائم للتسوية:** صف `update_failures` بيبقى + **علم التجاوز** المصرَّح به
  (سبب + وقت + هوية المالك). **مخطط منفصل:** إضافة `update_failures.acknowledged_by_operator
  INTEGER/TEXT` + `acknowledged_at TEXT`، **أو** جدول `acknowledgment_overrides`.
  **ده تغيير مخطط منفصل يحتاج موافقة — مش مُضاف هنا.** [مخطط منفصل]
- **تقدّم الحدّ بعده:** بعد التجاوز المصرَّح به، `compute_eligible_prefix` بيعامل التحديث
  كأنه مؤهّل (فقط بوجود علامة التجاوز) ⇒ الحدّ يتقدّم. **قبل** كده، الحدّ **واقف** عنده.
- **منع التخطّي غير المقصود/غير المصرَّح:** (1) مفيش تجاوز تلقائي؛ (2) التجاوز **يتطلب**
  صف/علامة صريحة؛ (3) مفيش `max+1`؛ (4) أي تحديث غير مؤهّل **بيحجز** البادئة (fail-closed).
- **مفيش تنفيذ لآلية skip في الـ ADR.**

### 18.7 دلالات الـ watermark والاحتفاظ

- **الـ watermark = `B_eligible` (حدّ مونوتوني).** **مونوتوني:** مايتراجعش أبدًا (بنكتب
  `newB` بس لو `newB > boundary`).
- **التفاعل مع التقليم:** التقليم بيشيل أقدم صفوف `processed_updates` [F]. الـ watermark
  **بيمنع** إعادة تنفيذ أي `update_id ≤ B_eligible` **حتى لو سجله اتقلّم**: الحلقة بتتجاهل
  أي `update_id ≤ boundary` **قبل** أي dispatch. ⇒ التقليم **آمن** بالنِسبة للتحديثات
  **تحت الحدّ**.
- **تحديث مكرّر تحت الـ watermark:** بيتجاهل (stale) — مفيش تنفيذ تاني. [A]
- **فجوات:** الـ watermark مش بيتأثّر بيها (بيتعامل مع ترتيب الاستقبال).
- **التسوية اليدوية (poison):** الـ watermark بيتقدّم **بس** بعد علامة تجاوز صريحة (§18.6).
- **إعادة التشغيل/التعافي:** الـ watermark محفوظ ⇒ الاستئناف منه ⇒ مفيش إعادة تنفيذ قديمة.
- **قيود صريحة:** (أ) الـ watermark **مش بيثبت** إقرار تيليجرام (سجل محلي [F])؛ (ب) بعد
  التقليم، لو الـ watermark **مش** محفوظ/اتفقد ⇒ ممكن إعادة تنفيذ قديمة ⇒ **الـ watermark
  شرط** لأمان التقليم؛ (ج) **مفيش تغيير احتفاظ في الـ ADR** — الـ watermark **مكمّل**
  للسجلات (السجلات بتدّي تفاصيل النتيجة).
- **مخطط:** `ACK_BOUNDARY_KEY` موجود [F]. لو احتجنا مفتاح watermark منفصل ⇒ `settings`
  (key/value) موجود ⇒ **مفيش تغيير مخطط** لده.

### 18.8 مواصفات الاختبار المطلوبة (تحوّل كل ضمان لاختبار)

### 22.2 هل آلية الاكتمال المُقترحة تقدر تفرّق؟

- **التصنيف المُقترح (v3) لا يعتمد على رجوع `process_update`** (G7)؛ بيعتمد على **نتيجة
  مُسجَّلة دائمة** في القاعدة (G12).
- بس فيه **فجوة بنيوية [G]:** المسارات **المُسجَّلة صراحةً** (G12) بتغطّي الحالات **المعروفة**،
  لكن **«مفيش handler مطابق» مابتسجّلش أي نتيجة** ⇒ يبقى **غير مؤهّل (fail-closed)**، **مش**
  «نجاح». **بس** كده تحديث زي `edited_message` (مش مؤهّل أبدًا) **بيحجز الحدّ للأبد**.
- **الحلول المُقترحة [A] (بروبوزال فقط — مش تنفيذ):**
  1. **`allowed_updates` صريح:** نمرّر `allowed_updates` في `get_updates` بالأنواع اللي
     عندنا لها handler (مثلًا `["message", "callback_query"]`) ⇒ تيليجرام **مايبعتش** الأنواع
     التانية ⇒ **مفيش تحديثات بلا handler** ⇒ الفجوة تختفي. **ده بروبوزال تغيير سلوك
     (فلترة على مستوى تيليجرام) — محتاج موافقة، ومش مُنفَّذ.** [A]
  2. **آلية تسجيل «مفيش handler»:** نضيف مسار **يسجّل `explicitly_ignored`** لأي تحديث
     **من غير نتيجة** بعد اكتمال المعالجة (مثلًا handler احتياطي `group` منخفض الأولوية،
     **أو** أداة تسجيل على مستوى التطبيق). **بروبوزال معماري — محتاج موافقة.** [A]
  3. **تسجيل الوصول:** نُسجّل **وصول كل تحديث** (`update_id`) عند السحب كـ «قيد المعالجة»،
     وبعد الاكتمال نُسجّل النتيجة. تحديث **وصل وخلّص** من غير نتيجة ⇒ **«مفيش handler»**
     ⇒ غير مؤهّل. **ده بروبوزال (يكتب صفوف لكل تحديث) — محتاج موافقة.** [A]
- **قرار v3:** **الفجوة لسه مفتوحة.** التصميم **آمن** (مفيش handler ⇒ **مش** نجاح صامت)،
  **بس** ممكن **يحجب الحدّ** (fail-closed). **لازم موافقة** على واحد من الحلول (١/٢/٣) قبل
  التنفيذ، **أو** قبول صريح بأن الأنواع غير المُعالَجة **هتُحجب** الحدّ. [G]

### 22.3 قواعد الأهلية الدقيقة

| الفئة | الشرط | مؤهّل للإقرار؟ |
|-------|-------|----------------|
| **معالَج بنجاح (نية دائمة)** | `processed_updates.outcome = durable_completed / durable_intent_recorded` | ✅ |
| **مكرّر** | `duplicate_completed` | ✅ |
| **تجاهل صريح مقصود** | `explicitly_ignored` **المكتوبة بواسطة handler فعلي** (رد/تنقّل/أمر/رفض تفويض/مرفق مرفوض) | ✅ |
| **فشل** | `failed_transient / failed_permanent / partial_or_unknown` (في `update_failures`) | ❌ (fail-closed) |
| **مفيش handler مطابق** | **مفيش أي صف نتيجة** | ❌ (fail-closed — **مش** نجاح) |
| **استثناء ابتلعه معالج الأخطاء** | `record_update_failure` بيسجّل `failed_*` (G11) | ❌ |
| **عملية ناقصة/غامضة** | `partial_or_unknown` | ❌ |

**قاعدة حاكمة [A]:** **أي تحديث من غير نتيجة مؤهّلة مُسجَّلة ⇒ غير مؤهّل.** «مفيش handler»
**مايتحوّلش أبدًا** لنجاح صامت.

## 23) آلية الاكتمال المُتحقَّق منها (حلّ §5)

- **PTB 22.8 [F]:** `Application._update_fetcher` بتاخد من `update_queue` وبتنادي
  `__process_update_wrapper`؛ الـ wrapper بينادي `update_queue.task_done()` في `finally`
  **بعد** ما `process_update` (وكل الـ handlers المتزامنة) تخلّص (G10). وكل الـ handlers
  الأساسية `block=True` (G9) ⇒ `process_update` **بيستنى** الـ handler.
- **⇒ آلية صحيحة [A]:** الحلقة المخصّصة:
  1. `await update_queue.put(u)`
  2. `await update_queue.join()` — **حاجز اكتمال حقيقي**: بيرجع بس لما `task_done()` تتنادى
     (يعني `process_update` خلصت للـ update، **نجاح أو فشل**).
  3. **تحديد النتيجة:** `outcome = db.update_outcome(u.update_id)` (أو `update_failures`).
  4. **مفيش نتيجة ⇒ «مفيش handler» ⇒ غير مؤهّل** (§22).
- **مهم [F]:** الحاجز بيثبت **الاكتمال** بس **مش النجاح** — لأن PTB بيبتلع الاستثناءات
  (G8/G11). الحكم النهائي **من القاعدة** (نتيجة مُسجَّلة)، **مش** من رجوع `process_update`
  ولا من `join()` لوحده.
- **تحذير [F]:** `await update_queue.put(u)` لوحده **مابيثبتش** الاكتمال (متوافق مع §3.3) —
  لازم `join()`.
- **`update_queue.join()` vs إشارة الـ wrapper:** `join()` هو **الأدق والأبسط** لأنه
  مضمون من المصدر (G10) ومايتطلبش لَفّ الـ handler. (لَفّ الـ handler بإشارة لكل `update_id`
  بديل، لكنه بيغيّر تسجيل PTB ⇒ أقل تفضيلًا.)

## 24) الإقلاع و`getWebhookInfo` (حقيقة مُتحقَّق منها)

- **تصحيح [F]:** `getWebhookInfo` **بتشتغل** لما البوت بيستخدم `getUpdates` (بترجّع `url`
  فاضي، G3) — **فبالتالي `getWebhookInfo` مش محجوبة** بالـ webhook. **بس `getUpdates`
  محجوبة** وقت وجود webhook فعّال (G1). ⇒ أي تصميم بيعتمد على `getUpdates` **قبل** حذف
  الـ webhook **فاسد**.
- **الترتيب الصحيح إلزاميًا:** `deleteWebhook` **قبل** أي `getUpdates` (G2). التفاصيل في §25.

## 25) الترتيب الصحيح للإقلاع (تصحيح §18.4) + سياسة الإقلاع

### 25.1 تصحيح الترتيب
- **خطأ v2 [G→مُصحَّح]:** «`getUpdates(offset=B+1, timeout=0)` **قبل** أي `delete_webhook`».
  **باطل** — تيليجرام **مابيسمحش** بـ `getUpdates` وقت webhook فعّال (G1)، والمشروع
  **مابيعملش** `set_webhook` (G5) فالحالة الفعلية: **مفيش webhook** عادةً، **بس** ممكن
  يكون فيه webhook قديم متبقّي من إعداد سابق/BotFather ⇒ لازم نتعامل معاه.
- **الترتيب الصحيح [A]:** `deleteWebhook(drop_pending_updates=False)` **أولًا** ⇒ بعدها
  `getUpdates(offset=...)`.

### 25.2 تسلسل الإقلاع الدقيق (5 حالات)

**القاعدة الحاكمة [A]:** **`deleteWebhook(drop_pending_updates=False)` أولًا** في **كل**
الحالات (آمن: مابيمسحش المعلّق، G15)، **وبعدها** `getUpdates(offset=...)`.

1. **مفيش حدّ محفوظ (أول إقلاع/قاعدة فاضية):**
   - `deleteWebhook(drop_pending_updates=False)` (احتياطي، يضمن مفيش webhook).
   - `getUpdates(offset=None/0)` ⇒ تسحب كل المعلّق ⇒ تتعالج عاديًّا.
   - **قرار السياسة (محتاج موافقة، §26):** إما (أ) نعالج كل المعلّق، أو (ب) نمسحه
     (`drop_pending_updates=True`) زي السلوك الحالي.
2. **فيه حدّ `B` + مفيش webhook فعّال:**
   - `deleteWebhook(drop_pending_updates=False)` (idempotent/no-op).
   - `getUpdates(offset=B+1)` ⇒ الاستئناف؛ أي معلّق `> B` يترجّع ويتعالج ⇒ **تعافٍ**.
3. **فيه حدّ `B` + فيه webhook فعّال:**
   - `deleteWebhook(drop_pending_updates=False)` ⇒ **بيشيل** الـ webhook **ومابيمسحش**
     المعلّق ⇒ التحديثات المعلّقة `> B` **تفضل عند تيليجرام**.
   - `getUpdates(offset=B+1)` ⇒ تترجّع ⇒ تتعالج ⇒ **تعافٍ**.
   - **لا نستخدم `drop_pending_updates=True` هنا.**
4. **فشل بين حذف الـ webhook وأول `getUpdates` ناجح:**
   - الـ webhook اتشال (خلاص مفيش webhook) والمعلّق **لسه عند تيليجرام** (لأننا
     `drop_pending_updates=False`) ⇒ بعد إعادة المحاولة/الإقلاع: `deleteWebhook` تاني
     (no-op) ثم `getUpdates(offset=B+1)` ⇒ **تعافٍ**. **مفيش فقد** للعمل المؤهّل.
5. **مهلة/شبكة ونتيجة غير مؤكدة:**
   - لو `getUpdates` **نجح** (استجابة وصلت) ⇒ الـ offset المؤكَّد اتقدّم عند تيليجرام
     (بس الحدّ المحلي مااتغيّرش) ⇒ إعادة الإرسال بنفس `offset` آمنة/idempotent (تيليجرام
     مايرجّعش أقل من الـ offset).
   - لو **فشل** (مفيش استجابة) ⇒ **مفيش** إقرار زيادة عند تيليجرام ⇒ إعادة المحاولة آمنة.

### 25.3 متى بتعتبر تيليجرام التحديث مؤكَّدًا [F] + ليه التسلسل ده مايضيّعش عمل مؤهّل
- **تيليجرام بيأكّد** لما نداء `getUpdates` **يستخدم `offset > update_id`** (توثيق Bot API
  + PTB `get_updates` docstring). يعني الإقرار بيحصل عند **إرسال** offset أعلى.
- **الترتيب المصحَّح آمن** لأن: (١) `deleteWebhook(drop_pending_updates=False)` **مابيمسحش**
  المعلّق (G15)؛ (٢) الإقرار بيتقدّم **بس** لما نبعت offset أعلى، واللي **بنحسبه** من الحدّ
  المؤهّل المحفوظ (عمل مؤهّل مُسجَّب)؛ (٣) لو انهارنا قبل إرسال offset أعلى ⇒ المعلّق
  **لسه عند تيليجرام** ⇒ إعادة تسليم. ⇒ **مستحيل** يضيع عمل مؤهّل بسبب التسلسل ده.
- **تحذير [F]:** الحدّ المحلي **مش** دليل إقرار (متوافق مع §18.1).

## 26) سلوك أول تشغيل وسياسة الحفاظ على المعلّق

- **الوضع الحالي [F]:** `drop_pending_updates=True` **مقصود وموثّق** (OHB2-02، `main.py`)
  ⇒ عند أول إقلاع (أو أي إقلاع) التحديثات المعلّقة عند تيليجرام **بتترمي**.
- **هل السلوك ده **لازم** لـ Option A؟** **لأ [A].** Option A **مابيتطلبش** رمي المعلّق؛
  ممكن نبدأ من `offset=None` ونسحب كل المعلّق ونعالجه. الرمي **موروث** من التصميم الحالي
  (قرار منتج OHB2-02)، **مش** متطلب تقني لـ A. (مع ملاحظة إن `_bootstrap` بتاع PTB بتعمل
  `delete_webhook` **دائمًا** [F G4] — بس **`drop_pending_updates` هو اللي بيرمي**، مش الحذف
  نفسه.)
- **آثار فقد البيانات [A]:**
  - مع الرمي: أي أمر/رسالة اتبعتت والبوت واقف **بتضيع** (مفيش معالجة). مقبول للاستخدام
    الفردي (المالك بيتعامل لايف).
  - بدون رمي: كل المعلّق يتعالج ⇒ ممكن **طوفان** أوامر قديمة + **تكرار** أوامر (لو أُعيد
    إرسالها) — وده اللي القرار OHB2-02 بيحمي منه.
- **أأمن افتراضي لو الحفاظ على المعلّق أولوية [A]:** **عدم الرمي** (`drop_pending_updates=False`
  دائمًا) + الاعتماد على الحدّ/الديدَب لمنع التكرار. **بس** ده **بيغيّر سلوك الإقلاع**
  المُراجَع (OHB2-02) ⇒ **محتاج موافقة منتج صريحة**.
- **اللي محتاج موافقة صريحة:** أي تغيير لـ `drop_pending_updates` الحالي (من True لـ False)،
  **أو** الإبقاء على True مع تصميم A (اللي بيقبل فقد تحديثات وقت التوقف). **مفيش تغيير
  تلقائي.**

## 28) المخاطر المتبقّية والقرارات المطلوبة

## 30) Stage 1 — ADR موحَّد لِـ«إقرار تيليجرام الأمين»

### 30.1 حدّ الموثوقية (Durability boundary) — التعريف الدقيق
- **التحديث يُعتبر «مُقِرًّا» (acknowledged) عند تيليجرام ⇔ نداء `getUpdates` لاحق يستخدم
  `offset > update_id`.** الإقرار بيحصل عند **إرسال** offset أعلى، **مش** عند كتابة محلية [F §18.1/§25.3].
- **الحدّ المحلي `B_eligible`** (`settings.acknowledgment_boundary`) = **دليل محلي** لآخر
  تحديث في أطول بادئة مؤهّلة. **مش** دليل إن تيليجرام استلم أي offset [F §18.1].
- **قاعدة الإقرار:** مايتقدّمش offset عند `getUpdates` لأعلى من `B_eligible + 1`، و`B_eligible`
  مبني على **نتيجة دائمة مُـcommit** في `processed_updates.outcome`، **مش** على رجوع `process_update`.

### 30.2 سلوك الحالات (المطلوب في Stage 1)
| الحالة | السلوك المحدَّد | المرجع |
|--------|----------------|--------|
| قبول دائم ناجح | `outcome ∈ {durable_completed, durable_intent_recorded, explicitly_ignored, duplicate_completed}` ⇒ **مؤهّل**؛ الحدّ يتقدّم | §18.1، §22.3 |
| معالجة دفعة جزئية | الحدّ = **أطول بادئة مؤهّلة**؛ أول غير مؤهّل **بيحجز** كل اللي بعده (head-of-line) | §8، §18.1 |
| استثناء handler | PTB بيبتلعه ⇒ معالج الأخطاء `handle_processing_error` ⇒ `record_update_failure` ⇒ `failed_*`/`partial_or_unknown` ⇒ **غير مؤهّل** | §22.3، §23 |
| SQLite BUSY/LOCKED | إعادة محاولة محدودة (ميزانية صغيرة)؛ استنفادها ⇒ **فشل مقفول** (`failed_transient`) ⇒ غير مؤهّل | §22.3 |
| فشل قاعدة دائم | **فشل مقفول** + تسجيل واضح ⇒ غير مؤهّل؛ **مفيش** تحويل لنجاح | §22.3، §23 |

### 30.3 قاعدة «أطول بادئة مؤهّلة متّصلة»
- بترتيب **الاستقبال** (مش رقميًا)، مش `max(update_id)+1`، والفجوات مقبولة [F §8، `update_outcomes.acknowledgment_boundary`].
- أول تحديث غير مؤهّل **بيحجز** الحدّ (حتى لو اللي بعده ناجح).

### 30.4 تمييز الإقرار عن التسليم الخارجي (إلزامي)
- **إقرار تيليجرام** ≠ **تسليم OpenHands**. إقرار التحديث معناه بس إنه **اتعالج لقرار دائم محلي**
  (سجل صندوق/طلب إنشاء/تجاهل مقصود)، **مش** إن البرومت وصل OpenHands.
- **مفيش ادّعاء exactly-once** لأي أثر خارجي (OpenHands/تيليجرام). تسليم الصندوق at-most-once
  بضمان CAS، والأثر الغامض بيفضل `unknown` بدون replay تلقائي [F §7/§12].
- **مفيش ادّعاء exactly-once إطلاقًا.**

### 30.5 فجوات/افتراضات غير محلولة (محفوظة كما هي)
1. **§22.2 (مفيش handler):** الحجب fail-closed مفتوح — محتاج موافقة على حل (١/٢/٣) أو قبول صريح.
2. **§26 (`drop_pending_updates`):** الإبقاء على `True` (يقبل فقد عند التوقف) مقابل `False` ⇒ **قرار منتج**.
3. **§25 (تغيير الإقلاع):** إلغاء Updater ⇒ `deleteWebhook`/`getUpdates` بنود إقلاع صريحة ⇒ **موافقة**.
4. **§28.4 (مخطط منفصل):** `ack_offset_submitted`/`ack_offset_confirmed` وعلم تجاوز poison ⇒ **تغيير مخطط منفصل**.
5. **نافذة الفشل غير القابلة للتجنّب:** مفيش تأكيد مطلق لنجاح نداء `getUpdates` بعد انهيار (§18.2).

### 30.6 بوابة Stage 2 (لماذا لسه محجوب)
Stage 2 (التنفيذ) **مش مصرّح به**: يلزم (أ) قرار معماري على **Option A** (`updater(None)` + حلقة
مخصّصة)، (ب) موافقة على **تغييرات المخطط** أعلاه، (ج) حسم قرارات §28. **مفيش تنفيذ لـ Stage 2 في

**حالة المراجعة:** إضافة **توثيقية** فقط. **مفيش تنفيذ**. **مفيش مراجعة مستقلة** (مراجعة ذاتية).

## 32) حلقة الاستطلاع المخصّصة (§23/§25)

- **التوزيع + الاكتمال:** `update_queue.put(u)` ثم `update_queue.join()` — الحاجز مضمون من مصدر
  PTB 22.8 (`__process_update_wrapper` بينادي `task_done()` في `finally`). الحاجز بيثبت **الاكتمال**
  بس **مش النجاح** ⇒ الحكم من القاعدة.
- **الإقلاع:** `deleteWebhook(drop_pending_updates=False)` (إعادة محاولة للأخطاء العابرة) ثم
  `offset = B+1` أو `None` (§25.2 — 5 حالات).
- **النتائج:** لكل تحديث `db.update_outcome(id)`؛ لو مفيش ⇒ `partial_or_unknown` (غير مؤهّل،
  fail-closed). الـ fallback (`handle_unmatched_update`) بيسجّل `explicitly_ignored` للتحديثات
  غير المطابقة **قبل** التجميع، فبتلاقي نتيجة مؤهّلة.
- **التثبيت:** `commit_batch_outcomes(pairs, now)` (نتائج + حدّ في معاملة واحدة) ثم تقديم الـ offset.
- **الفشل:** خطأ عابر في السحب/التثبيت ⇒ log + backoff + إعادة المحاولة؛ الحدّ والـ offset مايتغيّروش.
- **الإيقاف:** `SIGINT`/`SIGTERM` ⇒ `stop()` ⇒ خروج نظيف؛ `run_bot` بيضمن `stop`/`shutdown`.

## 33) حلّ فجوة §22.2 (Option 2) — بأمان

- **`handle_unmatched_update`** (TypeHandler في آخر group 0): بيتنادى **بس** لو مفيش handler مطابق
  (بما فيه الفشل: لو handler مطابق رفع استثناء، PTB بيروح لمعالج الأخطاء **ومايُكملش** الـ groups
  التانية ⇒ الـ fallback ما بيتنادىش).
- **ما بيكتبش فوق نتيجة محفوظة** (`update_outcome` موجودة ⇒ خروج) و**ما بيحوّلش استثناء لتجاهل**.

- **`allowed_updates`** (D1): `["message","callback_query"]` ⇒ تيليجرام مايبعتش أنواع مالهاش handler.
- النتيجة: تحديث غير مطابق ⇒ **مؤهّل** (`explicitly_ignored`) ⇒ **مفيش حجب أبدي**، وبلا أثر خارجي.

## 36) Stage 3 — الاحتفاظ الآمن (التقليم الواعي بالحدّ)

- **الخطر قبل:** `prune_processed_updates` كان بيشيل أقدم الصفوف **بغض النظر عن الحدّ**. كان آمنًا
  **بس** لأن الحدّ مش مربوط بحلقة (مفيش تقدّم offset مبني عليه). بعد Stage 2 بقى الحدّ **مؤثّرًا**
  ⇒ التقليم الأعمى بقى **غير آمن**.
- **القاعدة (مطبَّقة):** بنشيل صفوف `update_id <= الحدّ` **بس**، لأن الحلقة بتستأنف من `الحدّ+1`

- **`keep` (سقف إضافي):** بيسيب أحدث `keep` صف **من اللي `<= الحدّ`** بس؛ الذيل فوق الحدّ مايتأثّرش.
- **مفيش حدّ ⇒ no-op:** مفيش تقليم بلا watermark مؤكَّد (اتجاه آمن).
- **التنفيذ:** `Database.prune_processed_updates(keep, boundary)`؛ النداء في `_post_init` بيقرا
  `get_acknowledgment_boundary()` ويمرّره. اختبارات: `test_duplicate_update_dispatch.py` (4) +
  `test_app.py` (2). **إثبات طفرة:** شيل فلتر الحدّ ⇒ 1 يفشل؛ فرّغ فرع `keep=None` من الحدّ ⇒ 2 يفشلان.

# v6 — إصلاح F1 (فشل تشغيلي في مسارات العرض) — OHB2-STAGE4-F1-FAIL-CLOSED-OPERATIONAL-ACK-FIX

## 37) سياسة الفشل التشغيلي في `show_status`/`show_cost` (مطبَّقة)

**العيب المؤكَّد (F1):** `show_status`/`show_cost` كانوا بيسجّلوا `explicitly_ignored`
(نتيجة **مؤهّلة** للإقرار) لأي `conv is None` — بما فيه **الفشل التشغيلي** upstream
(5xx/429/مهلة/انقطاع). الأثر: تحديث عرض فشل تشغيليًّا كان بيتقبل كأنه اتعالج ⇒ الحدّ والـ
offset يتقدّموا فوقه ⇒ **مفيش إعادة محاولة** بعد التعافي، وسلوك غير متّسق مع
`open_conversation`/`copy_reply`/`full_reply` (§4/§7).

**السياسة المعتمدة (Option B — fail-closed)، مطبَّقة في `bot/handlers.py`:**

| الحالة | النتيجة | مؤهّل للإقرار؟ |
|--------|---------|----------------|
| فشل تشغيلي upstream: **5xx** | `failed_transient` | **❌** |
| فشل تشغيلي upstream: **429** | `failed_transient` | **❌** |
| مهلة/انقطاع اتصال (بلا `status_code`) | `failed_transient` | **❌** |
| أي فشل تشغيلي عابر مؤكّد آخر | `failed_transient` | **❌** |
| رفض نهائي مؤكّد: **404 / NOT_FOUND** | `explicitly_ignored` | ✅ |
| رفض نهائي مؤكّد: **403 / UNAUTHORIZED** | `explicitly_ignored` | ✅ |
| نجاح العرض (استرجاع + تسليم تيليجرام) | `explicitly_ignored` | ✅ |
| فشل تسليم تيليجرام | `failed_transient` | **❌** |
| فشل/غموض غير محسوم | `partial_or_unknown`/`failed_*` (fail-closed) | **❌** |

**نقاط إلزامية:**
1. الفشل التشغيلي في `show_status`/`show_cost` = `failed_transient` — **مش** رفض دائم، و**مش** تجاهل.
2. غير **مؤهّل** للإقرار عند تيليجرام (fail-closed).
3. الرفض النهائي المؤكّد (404/403/NOT_FOUND/DELETED/UNAUTHORIZED) يفضل `explicitly_ignored` **مؤهّل**.
4. **الفشل التشغيلي يقدر يحجب الحدّ** والتحديثات اللي بعده (head-of-line) — نتيجة **مقبولة** للسياسة fail-closed.
5. **التعافي** لازم يستخدم **الآلية المصرَّح بها** القائمة فقط: إعادة تسليم تيليجرام بعد الـ offset الثابت
   (تحديث الفشل **مايسجّلش** «معالَج» ⇒ إعادة التسليم تنفّذ تاني)، و/أو إعادة تشغيل الحلقة
   (استئناف من `B_eligible+1`). **مفيش** تجاوز تلقائي، **مفيش** `max+1`، **مفيش** طابور ديدَب جديد.
6. **§28.4 (مخطط `ack_offset_submitted`/`ack_offset_confirmed` + علم تجاوز poison): لسه مؤجّل وغير مُنفَّذ.**
   **مفيش** آلية تخطّي/تجاوز poison اتضافت.

**التنفيذ:** `bot/handlers.py` — دالة `mark_operational_failure` (تسجيل صارم `failed_transient`)،
و`show_status`/`show_cost` بقوا يستخدموا المسار المفصّل `_authorized_conversation_status` ويفرّقوا
الفشل التشغيلي (غير مؤهّل) عن الرفض النهائي (مؤهّل). **مفيش** تغيير في `bot/db.py`/`bot/polling.py`/
`bot/update_outcomes.py` (البنية fail-closed القائمة أُعيد استخدامها كما هي).
**الاختبارات:** `tests/test_stage4_f1_status_cost_operational_ack.py` (28 اختبار).

**حدّ متبقٍّ (موثَّق):** لو فشل OpenHands التشغيلي **دائم**، التحديث يفضل غير مؤهّل ⇒ الحدّ/الـ offset
يتوقّفوا عند أول تحديث عالق (حجب head-of-line) لحد التعافي أو تدخّل مصرَّح به. ده سلوك fail-closed
**مقصود** (نفس حدّ §22.2/§18.6)، **مش** عيب. لا يوجد مسار تجاوز تلقائي — التعافي يحتاج أن الفشل يزول
(إعادة تسليم ناجحة) أو قرارًا منفصلًا لتجاوز poison (§28.4، مؤجّل).
